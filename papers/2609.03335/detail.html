Latency-Aware Orchestration for Multi-Agent LLM Workflows on Heterogeneous GPUs — L2 #

Category note: L1 tags this as cs.DC and the algorithmic contribution is an online scheduling heuristic over a physical-execution-graph state space. The "algorithm" here is a systems scheduling policy, so this note treats the scheduling heuristic (Algorithm 1 + lexicographic key Eq 12) as the核心 method rather than a training recipe.

1. TL;DR #

A prediction-guided runtime turns concurrent multi-agent workflows into a

mutable physical execution graph: it forecasts per-(model,request,device)

cost, fuses same-deployment chains, coalesces model lifecycle actions across

workflows, and jointly schedules placement/order/lifetime under a live

heterogeneous pool — cutting burst makespan by 36.8% and saving up to

24.63 GPU-s/session.

2. Q1 / Q2 / Q3 #

Q1 — 痛点 (problem) #

Concurrent multi-agent workflows run on **small, fixed, heterogeneous GPU

pools** (private/cost-constrained deployment). Prior workflow schedulers act

on individual model calls once ready: they can reorder priority but cannot

(a) manage when a downstream model becomes available and (b) preserve

physical continuity across logical node boundaries. Two measured

consequences dominate:

  • Model-availability delay accounts for 77.3–85.5% of request waiting

    • under Parrot and Kairos; **model loading consumes more GPU time than token

    generation**, and idle residency adds another 28.1–33.0% of GPU time.

  • Repeated physical admission at same-model node boundaries produces a

    • large tail: 39–42% of the p95 session (97.1–155.1 s) is spent

    re-releasing/re-acquiring the backend at boundaries where the successor

    needs the same deployment.

Q2 — 方法 (method) #

Separate logical semantics (what must happen, which results are visible)

from state-dependent physical execution (scheduling unit, model-lifecycle

action, resource order, placement). Three stages operate on a bounded

planning window $\mathcal{W}_t$ of ready + immediate near-ready units:

  1. Predictor — maps (model op-graph, request config, device attrs) →

    2. $(\widehat{T}^{\text{run}}, \widehat{M}^{\text{peak}}, \widehat{T}^{\text{load}})$ via a graph encoder + 3 target heads, cached into buckets and propagated through dependencies to forecast release times.

  2. Constructor — workflow-local fusion of strictly-linear

    3. same-deployment chains, then cross-workflow coalescing of compatible

    lifecycle actions (one load/prefetch serves multiple isolated workflows),

    inducing an implicit candidate space $\mathcal{G}_t$.

  3. Scheduler — event-driven heuristic that jointly picks

    4. lifecycle/replica/device bindings and resource order on one predicted

    timeline, ranks plans by a lexicographic key $\Phi_t$, commits only the

    next executable prefix, and replans the uncommitted suffix from feedback.

    核心技术壁垒: the joint, cumulative-memory-feasible online construction

    of the graph and its schedule together — evaluating each transformation's

    cumulative effect on ready work, scarce devices, transient memory, and

    resident state at every predicted transition boundary (Eq 11), rather than

    scoring transformations in isolation. This is what no prior planner does.

    Q3 — 结果 (results) #

    • Burst: makespan 634.2 s (−35.8%/−36.8% vs Parrot/Kairos), overall p95

      • 587.0 s (−25.4–25.9%).

    • Lowest makespan at both Poisson rates (−12.4–13.1% and −1.6–6.6%), but

      • honestly loses some Poisson p95/model-scoped tails (global objective

      trades a local tail for earlier drain).

    • Up to 24.63 GPU-s/session saved, driven mostly by cut idle residency.
    • Predictor: 8.05% loading WAPE, 7.25% runtime WAPE, 97.94% ordering / 97.82%

      • window-fit decision accuracy.

    4. 作者证明 #

    This is a systems paper: 无形式化作者证明 — 仅实证. There is no

    convergence theorem, regret bound, or optimality proof. What exists instead

    is a feasibility construction — a set of invariants and constraints that

    any accepted plan must satisfy — plus a lexicographic ranking objective. A

    desirable-but-absent guarantee would be a competitive-ratio bound of the

    online heuristic against the trace-conditioned Oracle it compares to.

    方程物理意义 + 6 minimum checks #

    1. Eq 1 $\left(\widehat{T}^{\text{run}}_{m,r,g}, \widehat{M}^{\text{peak}}_{m,r,g}, \widehat{T}^{\text{load}}_{d,g}\right) = \text{Predict}(\mathcal{G}_m, r, h_g)$ — three separate heads; loading depends on deployment+device only, run/peak on request too. Check: dimensionality is per-(model,request,device), not workflow-level — this is what makes cross-device ranking possible.
    2. Eq 2 release $\widehat{r}_u = t$ if $u\in F_t$, else $\max_{v\in\text{pred}}\widehat{c}_v$. Check: near-ready units release when the slowest predecessor finishes (max, not min) — correct lower bound on start.
    3. Eq 3 fusible-chain condition (one-to-one adjacency, same $d$, config-compatible). Check: the one-to-one succ/pred constraint forbids fusing across a branch/join, so contraction cannot violate a dependency.
    4. Eq 4 $I^{\text{adm}}_c = \max_i I_i$, $O^{\text{adm}}_c = \max_i O_i$, $\widehat{T}^{\text{run}}_{c,g} = \sum_i \widehat{T}^{\text{run}}_{m(c),r_i,g}$. Check: admission reserves the max context (pessimistic, safe) but predicts release as the sum of runtimes (sequential under one lease) — the asymmetry is deliberate and consistent.
    5. Eq 5 $H^X_t(u) = \{\langle\alpha_X(d(u))\rangle, \langle\text{Reclaim}, \alpha_X(d(u))\rangle\}$ with $\alpha_F=\text{Load}$, $\alpha_N=\text{Prefetch}$. Check: exactly two lifecycle shapes per class (direct vs reclaim-then-load); ready→Load, near-ready→Prefetch is the correct eager/lazy split.
    6. Eq 11 cumulative memory: $R^{G,\pi}_{a,t}(\tau) + \sum_s x_{s,a} M^{\text{inc}}_{s,a}\mathbb{1}[\widehat{s}_s \le \tau < \widehat{c}_s] \le C^M_a,\ \forall a,\tau$. Check: the indicator sums only concurrently-active requests at each transition instant $\tau$, so it catches transient overload during a load/reclaim even when the steady-state resident set fits — the crux of feasibility.

      7. Additional constraints tying selection to placement (Eq 9), resource-order

      orientation (Eq 10), and feasible device domain (Eq 8) complete the

      admissible-domain definition; the objective is Eq 12:

      $$\Phi_t(G, \pi) = \left(-A_1, \dots, -A_K,\ \widehat{C}_F,\ -P_N,\ H^{\text{life}}\right)$$

      Physical meaning: lexicographic — first maximize admitted ready work per

      priority class ($-A_k$), then minimize latest ready completion $\widehat{C}_F$,

      then maximize timely prefetches $-P_N$, then minimize lifecycle overhead

      $H^{\text{life}}$. Ready work is never sacrificed for prefetch.

      7. 实现 cross-reference #

      [实现未公开] — the paper's footnote states "Code and data will be

      released upon acceptance," so no file:line citations are available.

      Reconstruction anchors for a future implementation, from the paper:

      • 核心技术壁垒 (elaborated): the hardest-to-replicate piece is the online

        • Propagate step (Algorithm 1 line 14) that serializes co-located

        operations and validates Eqs 9–11 cumulatively per transition boundary

        $\tau$. Getting the memory feasibility right requires modeling transient

        overlap (old weights + retained KV + engine buffers + incoming state

        coexisting during a load) — a steady-state check is insufficient and will

        produce OOMs that the adaptive $\rho_\kappa(t)$ term only patches after the

        fact.

      • 关键实现细节 (easy-to-miss tricks):
      • Two different output buckets for one unit: timing uses the smallest

        • bucket covering the 90th-percentile observed output length of recent

        same-node completions (optimistic), while admission always uses the

        configured output limit (pessimistic). Using one bucket for both

        silently breaks either latency accuracy or feasibility.

      • Fusion admits max context but predicts summed runtime (Eq 4): the

        • admission envelope is $\max_i I_i$ over the chain (worst-case), yet the

        release estimate is $\sum_i \widehat{T}^{\text{run}}$; conflating these

        over-reserves memory or under-predicts release.

      Closest open references (engine substrate only): vLLM 0.10.2 continuous

      batching, on which all systems including the baselines Parrot and Kairos run.
