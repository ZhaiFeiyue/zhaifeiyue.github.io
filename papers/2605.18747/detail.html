Code as Agent Harness — 作者意图蒸馏 #

1. TL;DR #

把 code 从「agent 的输出物」重定义为「agent 的运行底座」：可执行 / 可检视 / 有状态三性质让 code 成为 harness 接口本身。全篇最硬的诊断是——多数多智能体编码系统根本没有形式化、可查询的共享程序状态表示，这才是系统脆弱性的技术根源，而不是规模问题。478 篇引用，零自有实验。

2. Q1 / Q2 / Q3 #

Q1 — 痛点：自主性的瓶颈被错误归因给了模型 #

作者的起手式是一次归因转移。业界默认「agent 不可靠 = 基础模型推理不够强」，§1 para 2 明确否定：agent harness 指的是包住 LLM 的那层软件——工具、API、sandbox、memory、validator、权限边界、执行循环、反馈通道——「自主性的瓶颈不只是基座模型的推理能力，也是把模型输出连接到长程动作与持久状态的那套系统的可靠性」。

在这个框架下作者切出三个耦合但不同的东西，这个三分是全篇的概念地基：

元素内容研究现状
model-internal capabilities推理、感知、规划、模拟、评估被研究得最充分
system-provided harness infrastructure预定义工具、API、sandbox、memory、validator、权限、遥测、workflowharness engineering 的主战场
agent-initiated code artifactsagent 在任务循环内自己创建、执行、观察、修订、持久化、共享的代码对象（回归测试、临时工具、DSL 程序、可执行 workflow、可复用 skill、中间程序状态）作者称「relatively underexplored」，本篇的靶心

三个更具体的痛点，分别对应后面三层：

  1. 纯文本推理无法被 harness 检验（§2.1）。CoT 让模型同时负责分解问题和执行中间运算，而 LLM 对符号 / 逻辑 / 算术执行是不可靠的；更关键的是文本推理「几乎不给 harness 任何能力去验证中间状态、检视执行行为、跨步持久化计算进度」。
  2. 单步生成之外没有可靠机制（§3）。code 进入 agent loop 之后，问题从「生成正确程序」变成「模型判断 + 可变任务状态 + 人设计的 harness 基础设施」三者的交互。
  3. 多智能体的共享状态是隐式的（§4）。这是全篇最尖锐的一击，见 Q2 的技术壁垒段。

    4. Q2 — 方法：三层脚手架 + 一个诊断 #

    这是 survey / position paper，「方法」= 一套分类学 + 一个规范性立场。三层的排列顺序对应 code 进入 agent loop 的先后：

    Layer 1 — Harness Interface（§2）：code 作为模型与环境之间的介质。作者论证 code 的三个性质是功能性的而非记法性的——executable 意味着 harness 能验证模型意图；inspectable 意味着失败可被诊断并回灌；stateful 意味着交互历史不会在步与步之间丢失。同时钉死了 code 的非隐喻边界：程序、脚本、形式规范、证明脚本、API schema、工具定义、测试、仓库、模拟器、配置文件，以及由可执行系统产生 / 消费的 trace 和 log 都算 code；而原始感知、物理状态、人类意图、模型内部隐式推理不是 code——它们可以被 code 序列化、估计、验证或作用，但不能被混为一谈。

    Layer 2 — Harness Mechanisms（§3）：五个控制面 —— planning（轨迹控制）、memory & context engineering（状态管理）、tool use（受治理的动作/观测层）、PEV loop（Plan–Execute–Verify 控制回路）、Agentic Harness Engineering（对 harness 本身的测量与改写）。其中 PEV 是把前三者缝成一个闭环的统一框架：plan 阶段产出一份关于下一次状态转移的 contract（涉及哪些文件、要保持什么不变量、用什么命令验证、回滚点在哪、哪些操作有风险），execute 阶段在 sandbox + 权限分层里执行，verify 阶段用确定性传感器和人审 gate 判定状态是否可接受。

    Layer 3 — Scaling（§4）：从单 agent 扩到多 agent，共享的 code artifact 成为协调、评审、验证的公共工作台。

    核心技术壁垒（详见 §7）：把 §4.1–§4.2 三张表的 Harness Substrate 列当作一个分布来读，而不是当作一份清单——由此得出「多数文献停留在 implicit / file-only」的中心 gap，再把三个看似无关的现象（implicit convergence 最盛行、拓扑复杂度反而更高、context 管理机制层出不穷）全部归因到同一个缺失的抽象上。这个诊断动作本身，而不是分类学，是本篇不可替代的部分。

    Q3 — 结果：一个立场，加一串自我削弱的证据 #

    作者的新立场是 shared code-centric harness substrate：程序是多智能体领域里唯一「会执行」的产物，它产生客观的、非语言的信号，原则上足以锚定一个形式化的共享底座；但绝大多数系统在架构层面没有利用这个性质，反而让 agent 用自然语言去揣测代码质量。

    诚实之处在于，作者同时把削弱自己论点的证据摆了出来：QualityFlow 的 Imagined Execution（LLM 逐步模拟 Python 解释器、不真跑代码）在 MBPP 上达到 98%+ precision / recall；Self-Collaboration 的模拟 tester 与真编译器 ablation 表现几乎一致。作者称之为「a provocative empirical question」，并没有把它压下去。最终的处方是分流：语言推理走快路径，执行只在语言模拟结构上想象不出的失败模式（runtime crash、资源耗尽、边界条件、性能回退）上作为验证 oracle。

    3.1 全局分类学 #

    3.2 Layer 1：code 作为 harness 接口 #

    Paper 的 Figure 2（caption: "Overview of code as the harness interface, connecting agents to reasoning, action, and environment modeling through executable programs, tool calls, state tracking, and feedback traces."）。

    三栏分别是 §2.1 / §2.2 / §2.3。读这张图要看每栏底部那行小字——它们是三种角色各自的验证方式：「Code helps the agent reason」靠 Executor / Solver / Traces，「Code translates intent into action」靠 Robot / GUI-OS / API Tools，「Code makes env. inspectable and traceable」靠 Repo / Logs-History / Test Traces。作者在 §2.2 特意指出中间这栏的困难与左栏本质不同：reasoning 里解释器能直接判对错，acting 发生在部分可观测、动态演化的环境里，失败可能表现为无效状态转移、延迟反馈或静默执行错误——机器人去抓一个够不着的物体，不会抛任何 runtime exception。

    3.3 Layer 2 的控制回路：PEV #

    Paper 的 Figure 8（caption: "Overview of harness control through PEV loop."）。

    四个象限对应 §3.4.1–§3.4.4：Static Analysis（repo maps, specs, invariants, commands）→ Sandboxed Execution（isolated filesystem, shell, runtime, IDE）→ Deterministic Verification（linters, tests, static analysis, stack traces）→ Permissioned State Transition（read-only / sandbox-edit / full-access）。右下角那三级权限是全篇少数几个可以直接照搬进工程实现的东西：read-only 层做仓库浏览、检索、静态检视、日志分析；sandbox-edit 层做局部打补丁、跑测试、临时装依赖；full-access 层覆盖网络访问、凭证、部署命令、发包、破坏性文件操作、Git 历史改写——最后一层必须挂强制 HITL gate，因为它的后果会溢出 sandbox。

    作者把 harness 类比为 cybernetic governor：一个观察 agent 动作后果、并据此调节后续状态转移的控制层。它不是把错误信息转发给模型，而是通过 linter / parser / compiler / type checker / unit test / integration test / static analyzer / fuzzer / runtime monitor / CI 这一组确定性传感器观察仓库和执行环境，把轨迹变成 pass/fail、诊断、失败 trace、覆盖率缺口、安全告警、资源上限、策略违规这些可检视信号，然后在「继续执行 / 修补丁 / 要更多上下文 / 转交别的模块 / 降权限 / 升级给人」之间做决策。

    一轮 PEV 的状态机形态：

    stateDiagram-v2 [*] --> Plan Plan --> Execute : contract 已声明

    validation commands / rollback point) Execute --> Verify : 在 sandbox + 权限层内

    这张状态机里有两条作者反复强调的边。第一，Verify --> Plan 的存在就是他们主张「planning 与 debugging 不能分开」的理由——失败的验证会更新计划，而计划决定了哪些验证证据是有意义的。第二，repair / reflection / termination 都是 Verify 的后果而非独立阶段；reflection 只有在锚定于可执行证据时才可靠，agentic critique 应当解读传感器输出而不是替代它。

    3.4 Layer 3：多智能体扩展 #

    Paper 的 Figure 10（caption: "Overview of scaling the agent harness through multi-agent orchestration over code. The figure illustrates how role-specialized agents, shared code-centric substrates, execution feedback, and adaptive collaboration topologies address single-agent limitations in context, specialization, and self-correction."）。

    左上角列出三条单 agent 限制（context window 装不下整个 codebase + 交互历史 + 执行 trace；一个通才 agent 同时做规划/合成/测试/评审/调试效率低；缺少独立的协调与验证通道导致无法可靠自查），右侧是应对：四种交互模式（Debate / Critique / Adversarial / Collaborative）、四种启发式拓扑（Chain / Cyclic / Hierarchical / Star）、三种自适应拓扑（动态 agent 池扩缩 / 反馈驱动 DAG 重构 / 运行时自组织）。

    左下角那块红色区域是全篇的诊断落点：Harness Representation 的四个层级——File-only / Execution-based / Repository-based / Blackboard，以及它们各自导向的 Program-State Convergence 判据（Correctness / Security / Performance / Consensus）。作者要论证的是：绝大多数系统落在最左边的 File-only，而右侧那些花哨的自适应拓扑，是缺少形式化底座之后的代偿而非进步。

    4.2 最小检查 #

    Check 1 — $s(r)$ 的边界行为自洽。 $m(r)=0 \Rightarrow s(r)=1$，$m(r)=tc(r) \Rightarrow s(r)=0$。§4.3.2 描述的停机规则「continues iterating until the maximum score reaches 1.0」因此等价于零观测失配，不是一个宽松阈值。这一点作者没写，但公式与停机语句是一致的。

    Check 2 — $s(r)$ 的归一化有未讨论的副作用。 用比率而非绝对失配数，好处是不同 $tc$ 下的候选可比；代价是一个只被 2 条用例测过且 0 失配的候选，与被 100 条用例测过且 0 失配的候选得分完全相同（都是 1.0）。当 $tc(r)$ 随候选变化时，$s$ 并不单调反映真实正确性。作者引用该公式时未讨论这一点。

    Check 3 — $\lvert B_k - S_k \rvert$ 的量纲未定义。 仓库状态是离散结构（文件树 + 内容 + 版本），论文没有给出 $S_k$ 所处的度量空间，因此绝对值号在此是隐喻性的。SyncMind 实际报告的是 out-of-sync recovery 类指标。本篇原样沿用了符号而没有补上度量定义——考虑到这是全篇关于状态的唯一形式支点，这是个可被追问的薄弱处。

    Check 4 — 三处属性列表互不一致。 标题承诺 executable / verifiable / stateful；§2 para 2 论证的是 executable / inspectable / stateful；§5.2.7 收尾给出四条 executable / inspectable / stateful / governed。verifiable 被静默换成了 inspectable 与 governed，全篇未做说明。这不是笔误级别的问题：verifiable 与 inspectable 在作者自己的框架里恰恰是两件事（§5.2.2 的整节就在论证「有可执行反馈 ≠ 验证充分」）。

    Check 5 — 中心 gap 缺少可证伪的计数。 「the majority of the literature resides in the implicit/file-only category」是全篇最重的经验主张，但没有给出任何计数或百分比。可核对的证据只有 Implicit/File-only 子块里点名的 7 个系统（ChatDev、MetaGPT、FlowGen、MapCoder、CodeCoR、SEW、CodePori），加上 Table 9/10/11 的 Harness Substrate 列（合计约 25 个系统，且三表有重叠）。读者要自己去数，而分类边界（例如「Execution, implicit」算哪一类）由作者定义。

    Check 6 — Trend 5 的因果方向被作者主动弱化。 「拓扑复杂度与 harness 状态形式化程度反相关」的证据是：L2MAC（最清晰的形式化底座）用最简单的顺序链；EvoMAC / SEW（隐式状态）发展出复杂自适应 DAG。样本 $n=4$，且是相关性观察。作者用的措辞是「topology complexity is partially a symptom」——已经把因果强度调低了，这个自我限制是诚实的。

    Check 7 — Trend 3 是对自身论点的反向证据，作者承认但未量化。 98%+ 的 imagined-execution 精度直接冲击「可执行反馈是差异化优势」这一核心论点。作者的化解是「执行反馈的价值在各失败模式上不均匀」，并列举了语言模拟结构上想象不出的四类（runtime crash / 资源耗尽 / 边界条件 / 性能回退）。但这四类在真实失败分布中占多大比例，全篇没有任何数据。处方（快路径 + 按需 oracle）因此是合理的猜想而非被证实的结论。

    可以被界定但作者没做的量：给定四个表征层级和六种收敛判据，完全可以报告一个 systems × representation-level 的列联表，以及「实现 X 层级表征的系统在 Y 判据下的收敛率」。这是把中心 gap 从修辞变成可证伪主张所需的最小工作量，本篇没有做。

    5. 实验与数据 #

    本篇没有实验。 作者自己没跑任何 baseline、ablation 或 sweep。功能上等价于「实验」的产物是 §4.1–§4.4 对约 25 个多智能体系统沿统一维度的表格化拆解——中心 gap 与七条 trend 全部是从这几张表的列上读出来的。因此这一节展示的是表本身，以及本篇转述的（全部有出处的）数字。

    7.2 核心技术壁垒 #

    最难复制的不是三层分类学——分类学任何人读完 478 篇都能画出一个版本。真正难的是把 Harness Substrate 这一列当成一个分布来读这个动作，以及随之而来的三重归因收束。

    具体说：作者先把约 25 个多智能体系统按 Harness Substrate / Agent Roles / Interaction Mode / Topology / Execution Feedback / Convergence 六个维度拆成 Table 9/10/11——这个粒度是刻意的，不是描述性的。然后不去逐系统评优劣，而是回头统计这些列的取值分布，得出「多数落在 implicit / file-only」。最后——这一步才是壁垒——把三个表面上毫不相干的现象全部归因到同一个缺失抽象上：

    • implicit convergence 最盛行（§4.3.2）→ 没有客观状态表征，就没有原则性停机判据；
    • 拓扑越来越复杂（§4.4 Trend 5）→ 底座不可查询，agent 只能靠更丰富的交互模式来补状态信息；
    • context 管理机制层出不穷（§4.4 Trend 6）→ L2MAC 的 Control Unit、MetaGPT 的 pub-sub 池、SoA 的 agent 池扩缩、Cogito 的三层记忆，都是同一个问题的不同代偿。

    这个「三症一因」的收束要求先以正确的粒度建好表，再抵住逐系统点评的诱惑。它无法从任何单篇被引论文里读出来，只能从横向比较中浮现——这是本篇不可替代的部分，也是它作为 position paper 而非 literature list 的全部价值所在。

    副产品是一个可直接使用的诊断问题：看一个多智能体编码系统，先问「它的共享程序状态是什么，agent 能不能查询它」——如果答案是「最近一次对话上下文里的那份代码」，那么它后续所有的拓扑创新与 context 工程都应被读作代偿而非进步。

    7.3 关键实现细节 #

    三个容易被读过去但直接决定系统行为的点：

    （1）AgentCoder 的 Test Executor 不是 LLM，是一个确定性 Python 脚本。 作者把这一点单独拎出来作为该设计的关键属性——在一篇讲 LLM agent 的综述里，承重构件是一段普通脚本。它干净地把推理与执行分开，让反馈信号锚定在客观程序行为上。与之配套的是 Test Designer 独立于代码生成测试，针对的是 mode collapse：agent 有偏的测试会放过它自己有 bug 的代码。QualityFlow 的 Test Quality Checker 把这个防护提到元层（在合成测试被当作反馈使用之前先过滤它们），CANDOR 的 Panelists 则对着自然语言规范而非代码审计 oracle 正确性，刻意避免被错误实现污染。

    （2）L2MAC 靠「不覆盖写 + 精确切片」解决 context 问题，而不是靠扩大窗口。 file store $D$ 永不覆盖、只扩展和修订，因此天然是一份版本历史；Control Unit 在指令步之间重置上下文窗口，给每次新调用的是既往进度的定向摘要 $M_{rs}$ 而非完整对话史；接近容量时把部分结果写回 $D$ 并以压缩视图重新初始化，还会显式告诉 LLM 在剩余上下文余量下该读哪些文件、跳过哪些。加上 evaluator 作用于整个 file store 的 $E(D)$——语法失败因此能阻塞整条指令流水线，而不只是给某个文件加个注记。这套组合是「fresh-context agent 链」能成立的全部原因：状态住在 $D$ 里，$M_{rs}$ 只是指向它的指针加摘要。

    （3）QualityFlow 的 revert 机制是被调查系统中唯一显式管理状态历史的。 初始代码产物永不被覆盖，因而当调试轨迹开始劣化质量时，系统可以回滚到先前的共享 harness 状态。其余所有系统都只会向前走。这条与 §5.2.3 提出的 change contract（每次变更声明：改了哪个组件、针对哪个失败模式、预测什么改进、必须保持哪些不变量、什么评测能证伪它、怎么回滚）是同一个思路在两个尺度上的体现——一个在任务态，一个在 harness 态。
