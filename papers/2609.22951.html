AgentRouter — L3 相关性综合（Mode A） #

目标实体：2609.22951（AgentRouter，步级异构模型路由）。 相关集合（8 篇，均属 agent 类）：RouteLLM(2406.18665)、Reflexion(2303.11366)、 MetaGPT(2308.00352)、AutoGen(2308.08155)、SWE-bench(2310.06770)、 LLM-MA Survey(2402.01680)、Autellix(2502.13965)、MAST(2503.13657)。

相关论文 #

把相关集合按"与 AgentRouter 的关系类型"分成四层，而非一字排开——这决定了后文每条 delta 的可比性：

  1. 同谱系路由器（直接基线）——RouteLLM (2406.18665)。AgentRouter 的正面对标对象：两者都把"模型选择"重构成一个轻量分类问题。RouteLLM 学一个 $P(\text{win}_s\mid q)$ 的二元偏好预测器，用单一阈值 $\alpha$ 在强/弱两模型间切换 [2406.18665]；AgentRouter 把这个思路从"每条查询一次"推进到"每条轨迹的每一步"、从二元推进到四档 [2609.22951]。RouteLLM 既是 AgentRouter 的实验基线（per-step 应用只拿到 31.4% 降本），也是它最该被公平性质询的参照（见「可攻击面」）。
    1. 被路由的底物（轨迹/工作流生产者）——Reflexion (2303.11366)、MetaGPT (2308.00352)、AutoGen (2308.08155)。这三篇定义了 AgentRouter 赖以成立的"多步轨迹"本身。MetaGPT 的 SOP 把任务拓扑固定为 PM→架构师→工程师→QA 的预定顺序流水线 [2308.00352]——正是 AgentRouter "步序列在路由时已知"假设的理想形态 [2609.22951]。AutoGen 则相反，用 auto-reply 循环把"对话本身当 control plane"、动态生成下一步 [2308.08155]——这恰好落在 AgentRouter 自述的 scope 之外。Reflexion 跨 trial 重置环境、靠口头反思改写策略 [2303.11366]，其质量来自强 backbone 的涌现自诊断能力，是"不能随便降档"的典型步。
      1. 正交基础设施（服务层）——Autellix (2502.13965)。与 AgentRouter 处在不同平面：AgentRouter 是控制平面（选哪个模型），Autellix 是服务平面（何时、在哪个 engine 上跑这次 call）[2502.13965]。二者都利用"同一轨迹/program 内 call 的结构"，且 Autellix 明确把"不同角色用不同模型"列为 future work [2502.13965]——这正是 AgentRouter 填的空，故二者高度互补又存在耦合代价。
        1. 外部诊断/定位坐标——SWE-bench (2310.06770)、LLM-MA Survey (2402.01680)、MAST (2503.13657)。它们不与 AgentRouter 竞争，而是给它定坐标：SWE-bench 解释了为何代码域是 AgentRouter 最差的域（63.8% 降本）——真实代码任务的墙是长上下文定位而非片段合成 [2310.06770]；Survey 给出多智能体设计空间的四轴分类，让我们能说清路由属于哪一格 [2402.01680]；MAST 提供了一张"降档会引入哪些失败模式"的清单 [2503.13657]。

          2. 本篇 vs 相关论文的 delta #

          vs RouteLLM —— 粒度跃迁 + 一处正面矛盾 #

          新增量：(a) 路由单位从 query → trajectory step；(b) 档位从 binary → 4-tier；(c) 引入轨迹感知特征 $f_{\text{ctx}}$ 与依赖感知标签，捕捉"步 $t$ 的决策影响步 $t{+}1$ 上下文"这一单轮路由器结构性缺失的信号 [2609.22951]。

          一处可登记的矛盾：RouteLLM 的核心卖点是"路由器学到的是查询内在复杂度特征、可跨模型对免重训迁移"[2406.18665]；AgentRouter 却报告模型池一变就需重训、且跨框架（LangGraph/CrewAI→AutoGen）掉 6–9% 准确率 [2609.22951]。

          矛盾根源：两者的"泛化"是沿不同轴的。RouteLLM 固定查询分布（Chatbot Arena），只换强/弱模型对，于是迁移成立 [2406.18665]；AgentRouter 的泛化挑战是换智能体框架，而框架决定了步/轨迹分布本身。换模型对 ≠ 换轨迹分布，二者各自在自己的实验范围内都对，但 RouteLLM 的"免重训迁移"不能被 AgentRouter 继承。另一条数字也源于此：RouteLLM 在单轮 MT Bench 上拿到 3.66× 降本（≈73%，保 95% 质量）[2406.18665]，而同一个 RouteLLM 被 per-step 套到智能体轨迹上只剩 31.4% [2609.22951]——差距正是 AgentRouter 论证的分布外退化，而非 RouteLLM 方法本身失效。

          vs 三个框架（Reflexion / MetaGPT / AutoGen）—— "可路由性"由框架的规划风格决定 #

          AgentRouter 的核心假设"步序列可在路由时知晓"不是普适的，它的成立度反比于框架的动态性：

          • MetaGPT：SOP 预定工作流，角色与中间制品在执行前即固定 [2308.00352]——AgentRouter 的最佳适配面。甚至更强的 delta 在于：MetaGPT 已把每步贴上角色标签（PM/架构师/工程师），而 AgentRouter 的主导特征恰是 $f_{\text{type}}$（移除掉 12.3 准确率点）[2609.22951]——暗示在 SOP 框架里"角色身份≈任务类型"，12M 分类器可能被一张静态角色→档位表平替。
          • AutoGen：动态群聊由 GroupChatManager 运行时选下一发言者 [2308.08155]，未来步不可预见——这正是 AgentRouter §5 自述的"全在线场景落在 scope 外"。因此 AgentRouter 在 AutoGen 上掉 6–9% 不是意外，而是其假设被 AutoGen 的设计直接违反的可预测后果。
          • Reflexion：质量来自强 backbone 的涌现自诊断，弱 backbone 下增益归零（starchat 0.26→0.26）[2303.11366]。这与 AgentRouter 的降档逻辑构成张力：把格式化步路给 7B 安全，但把规划/反思步降档会抹掉正是让框架有效的那层能力。AgentRouter 的非对称损失 + 给 14.2% 的步保留 Tier 1 [2609.22951]，本质就是为保护这类"涌现步"而设计的护栏。

          vs Autellix —— 互补的两平面，但切换有耦合代价 #

          Autellix 把 OS 的 LAS 调度提升到 program 级，按累计服务排优先级，4–15× 吞吐 [2502.13965]；它不碰模型选择，并把异构模型留给 future work [2502.13965]。AgentRouter 正好补上这块。但两者叠加存在一处未被任一方量化的摩擦：AgentRouter 每轨迹中位 3.2 次档位切换 [2609.22951],而切换模型=切换 engine=打断 Autellix 赖以提速的 intra-program KV-cache locality（intra-program 命中 >90%，跨则指数衰减）[2502.13965]。单看降本，AgentRouter 对；单看吞吐，切换是成本——联合目标尚无人写。

          vs SWE-bench —— 给"代码域最差"提供了机理解释，并质疑质量基线 #

          AgentRouter 承认代码生成降本最差（26.3% 的步需 Tier 1 vs 文档域 8.7%）[2609.22951]。SWE-bench 给出了机理：真实代码任务的瓶颈是"在 token 之海里定位该改的几行"，更多上下文甚至降低解决率，模型系统性 under-edit [2310.06770]。更尖锐的是，SWE-bench 下即便 GPT-4 也只解 <2% [2310.06770]——这动摇了 AgentRouter "frontier-only = 100% 质量天花板"的隐含基线：在 frontier 本身就接近地板的域里，"保留 97.3% 的 frontier 质量"是一个域相对的、可能很低的锚。

          vs LLM-MA Survey —— 填了分类表里一个没有的格子 #

          Survey 的四轴（接口/画像/通信/能力获取）里，模型选择最接近"能力获取"但其实无处安放 [2402.01680]。AgentRouter 引入的是一条 Survey 未列的新轴：步内异构模型分配。而且它直接回应了 Survey 点名的 §6.4 scaling/orchestration 开放挑战——Survey 把"每个 agent ≈ 一次 GPT-4 调用"的总资源增长列为未量化难题 [2402.01680]，AgentRouter 把它量化并砍了 72%。

          vs MAST —— 引入新失败模式，却只用聚合指标体检 #

          MAST 把多智能体失败编码成 14 模式/3 类，并证明"廉价模型产出微错中间结果→下游在被污染上下文上推理"正是 inter-agent misalignment（FC2）的典型 [2503.13657]。AgentRouter 的依赖感知标签 + <4% 回退就是冲着这条 cascade 设计的 [2609.22951]。但 delta 是方向相反的风险：AgentRouter 只测端到端完成率，不测失败模式分布 [2609.22951]，因此无法判断自己是否在用聚合指标掩盖新引入的 FC2 失败。MAST 还证明孤立修复只带来 +9.4~15.6% 且完成率仍低 [2503.13657]——AgentRouter 本身就是一个孤立的（成本）优化，很可能移动而非消除失败分布。

          可攻击面 #

          对 AgentRouter 具体主张的逐条反驳（default-to-skeptical）：

          1. "97.3% 质量保留"站不住全部重量。 同表的 DAAO 以 36.2% 降本换到 98.1% [2609.22951]——per-step 路由相对 per-trajectory provisioning 确实引入了非零质量风险。更关键的是"质量"由 F1/pass@1/事实准确率等自动指标度量，而 Reflexion 已暴露这类指标的假阳性问题（MBPP Python 单测 16.3% 假阳率，导致把错解判过）[2303.11366]，SWE-bench 也显示通过的补丁常是浅层 under-edit [2310.06770]。若 97.3% 的分母本身漏检了微错，这个数字是乐观偏置的。
            1. "最小充分档"标签与"不可分解"自相矛盾。 AgentRouter 一边强调端到端质量 $Q(\tau,\pi)$ 不可分解为逐步项 [2609.22951],一边用"每步质量落在前沿 2% 以内"的逐步阈值造标签 [2609.22951]。若 $Q$ 真不可分解，逐步 2% 的充分性无法推出端到端 97%——论文自己在 作者证明 节承认没有任何形式化上界，97% 纯属经验 [2609.22951]。依赖感知标签缓解但不消除这个逻辑缺口。
              1. "<4% 回退 vs 84.6% 准确率"的自洽依赖一个未验证的裁判。 该叙事成立的前提是"多数错误为无害的过度配置"[2609.22951]，但生产中触发回退的是一个 LLM-as-a-judge 代理。MAST 的实测表明 LLM 裁判没有 few-shot 校准只有 κ=0.58、校准后才到 0.77 [2503.13657]——一个弱裁判会系统性漏报质量违例，把本该回退的轨迹算成"通过"，从而同时压低回退率并虚高质量。AgentRouter 未报告其 judge 的 κ。
                1. 跨框架的"降本仍达 58%"是选择性叙事。 AutoGen 上报告了 6–9% 准确率下降和 58% 降本，却没报质量下降 [2609.22951]。准确率降=更多误档，在非对称损失下虽偏向过度配置，但 OOD 分布下这一偏向未必保持——58% 的省钱完全可能伴随未测量的质量损失。
                  1. 对 RouteLLM 的碾压部分来自档位数而非轨迹感知。 实验里 RouteLLM 被限定为二元（GPT-4o/Llama-3-8B）、无中档 [2609.22951]，而 RouteLLM 原文明确把 N-way 路由列为 future work [2406.18665]。把 AgentRouter 的 4 档优势与"步级 vs 查询级"优势混在一个 71.8 vs 31.4 的对比里，夸大了后者的独立贡献——一个公平的四档 RouteLLM 基线缺席。

                    2. 生态位 #

                    范式定位。 AgentRouter 坐在两条谱系的交点：向上接模型路由谱系（RouteLLM 的二元查询路由 → 多档步级路由）[2406.18665]，向下接智能体基础设施（框架产出轨迹、Autellix 服务轨迹）。它把自己框为"轨迹级的资源自适应推理"——按步匹配算力与复杂度，而非对整条工作流施加统一模型选择 [2609.22951]。这是一次从"每应用/每查询选一个模型"到"每步异构分配"的粒度范式迁移。

                    前提已被独立佐证。 "14.2% 的步需前沿却占 48.3% 成本"这一核心偏斜 [2609.22951]，与 Salim 等的 Tokenomics（59.4% token 花在 Code Review 阶段，论文自引）相互印证，也与三个框架的 backbone 敏感性数据一致——MetaGPT 换到弱 backbone 可执行性崩到 1.4 [2308.00352]、AutoGen 在弱 backbone 上多 agent 增益更大 [2308.08155]，都说明"能力需求在步/角色间高度不均"是真实存在、可被利用的结构。

                    采纳面的硬伤：闭源。 12M、<5ms、重训 <2 GPU-hours 的轻量化本应利于落地 [2609.22951]，但实现未公开 [2609.22951]。而本相关集合里 RouteLLM [2406.18665]、MetaGPT [2308.00352]、AutoGen [2308.08155]、SWE-bench [2310.06770]、MAST（pip install agentdash）[2503.13657] 全部开源。在一个以开源框架/基准为流通货币的子领域里，闭源 + 真正壁垒在于难复制的"穷举四档执行 + 反事实归因"标注管线 [2609.22951]，意味着其生态位更可能是"被同类开源工作（如 Aragog 式 per-stage 路由）复刻取代"，而非自身成为事实标准。

                    未探索方向 #

                    从这个集群可组合出的 hybrid / adaptive 方向：

                    1. 在线/动态路由 × 非 clairvoyant 调度。 AgentRouter 的最大 scope 缺口是"未来步动态生成"场景 [2609.22951],而 AutoGen 的动态群聊 [2308.08155] 与 Reflexion 的多 trial [2303.11366] 正是这类。把 AgentRouter 的逐步决策改造成增量式、与 Autellix 的 non-clairvoyant program 调度（仅依赖已完成 call 的 runtime）[2502.13965] 同构，可让"选模型"和"排调度"共享同一套运行时轨迹估计。
                      1. 路由-服务协同设计（联合目标）。 把 AgentRouter 的档位切换代价与 Autellix 的 locality 收益放进一个目标函数：$\min$(推理成本 + 档位切换引发的 cache-miss/按调用初始化开销)。当前 AgentRouter 的 3.2 次/轨迹切换 [2609.22951] 与 Autellix 的 >90% intra-program 命中 [2502.13965] 在联合部署下直接冲突，是一个干净的、可量化的优化问题。
                        1. 失败感知路由（用 MAST 当路由信号）。 不止用完成率，而把 MAST 的 14 失败模式作为路由的额外约束——对易触发 FC2 reasoning-action mismatch 的步强制升档，并在评测里报告失败模式分布而非仅聚合完成率 [2503.13657]。这直接补上「可攻击面」第 1、5 条暴露的盲点。
                          1. 框架原生路由（角色身份 ≈ 任务类型）。 既然 $f_{\text{type}}$ 是主导特征且 MetaGPT 已在 SOP 里显式给出角色 [2308.00352]，一个值得做的消融是：用静态"角色→档位"表（Aragog 式 per-stage）替掉 12M 分类器，测其能捕获多少 $f_{\text{type}}$ 的 -12.3 收益 [2609.22951]。若接近，则在结构化框架里根本不需要训练分类器——这会大幅降低采纳门槛并绕过闭源壁垒。
                            1. 代码域的上下文定位专门化。 SWE-bench 的"collapsed context（±15 行）反而提升解决率"[2310.06770] 提示：AgentRouter 的 $f_{\text{ctx}}$ 不应只当作"占用率越高越要升档"的单调信号，而应与定位质量解耦——高 $f_{\text{ctx}}$ 的长上下文代码步，先做上下文裁剪再路由，可能让一个较便宜档也胜任，从而把 AgentRouter 最差的代码域（63.8%）[2609.22951] 往上拉。
