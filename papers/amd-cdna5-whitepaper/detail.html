1. TL;DR #

CDNA 5 把部署单元从 8-GPU 节点抬到 72-GPU 单跳交换共享内存 pod：256 个 WGP 以

Wave32 + 双倍 SIMD 宽度换来 MXFP4 40.26 PF、432 GB HBM4 @ 23.3 TB/s、每 GPU

3.6 TB/s UALoE。24 页零实测。两处高代价的静默变更：MXFP6 从与 MXFP4 同速掉到与

MXFP8 同速；MFMA 全族被 WMMA 取代。

2. 三问 #

Q1 痛点 #

白皮书的问题陈述不是"算力不够"，而是部署粒度不对。三条论据：

  1. 单 token 的代价：LLM 参数进入万亿级后，每输出一个 token 需要"trillions of

    2. computations and hundreds of billions of DRAM requests"（白皮书；无模型规模、

    无 batch size、无 endnote，属于量级修辞而非规格）。

  2. MoE 改变了配比：MoE"总参数多、每 token 只访问一小部分"，直接改变

    3. compute:memory-bandwidth 的典型关系（白皮书）。这是文档里唯一一处点名的

    workload 结构性变化。

  3. 8-GPU 一次性部署已经不够：客户"can no longer meet the demands … by deploying

    4. GPUs one system at a time"，性能取决于 compute / memory / network / power /

    cooling / software / operations 作为一个机架级系统协同工作（白皮书）。

    代际对照说得很直白：MI355X 的机架是多个 8-GPU 系统用 RDMA over Ethernet 拼成的

    scale-out 集群；MI455X 的机架是一个 72-GPU 的 scale-up 共享内存 pod。

    推理收益被明确限定在"models that don't fit within an 8-GPU node"。

    • 计算单元换血：每 XCD 的 32 个 Active CU"被同等数量的 Work Group Processor

      • 取代"，Wave64 换成 Wave32，每 WGP 4 个 32 线程 SIMD + 4 个标量单元，每时钟可

    • 数值格式下探到可训练的 FP4：共享 scale 的 block 可以是 16 或 32 元素，

      • 且 MXFP4 新增分数 scale；白皮书的原话是"Block-level fractional scaling

      enables practical FP4 training, reducing quantization error vs. full-tile

      scaling"——这是全文唯一一处把新格式与训练（而非仅推理）绑定的论断。

    • 带宽放大：12 stack HBM4（接口位宽 1024→2048 bit/stack）、192 MB L2 @

      • 54 TB/s、96 MB LDS，加上两个减流量机制——读多播到多个 WGP、TDM 直接

      LDS↔DRAM 传输（不经中间寄存器）。

    • 把机架变成一台机器：36 条 400 Gb/s UALoE 链路 + 12 台以太网交换机全连接，

      • 任意两 GPU 恰好一跳；split DMA 让通信库无需感知 UALoE 拓扑。

    "isn't intended for general-purpose networking, but only for GPU-to-GPU memory

    transactions across short links"，所以控制逻辑与数据缓冲比完整以太网 NIC

    "much more compact"。这条取舍是 72-GPU 共享内存域在物理上成立的前提，也是最难

    被追赶的部分——它要求同时握有 GPU 封装、fabric 协议（Infinity Fabric over

    Ethernet lanes）、交换机与整机架设计。详见 §7。

    4. 作者证明 #

    无形式化作者证明 — 仅广告数字。全文 0 个公式、0 个性能投影模型、0 个实测

    点。因此本节做的是白皮书唯一可被证伪的东西：规格表的内部自洽性。下面的

    推导全部只用白皮书自身的数字（外加两处 ISA 手册交叉验证），任何读者可复算。

    4.1 符号 #

    符号含义值（白皮书）
    $N_{\text{WGP}}$每 GPU 的 Active WGP 数256
    $N_{\text{SIMD}}$每 WGP 的 SIMD 数4
    $W_{\text{lane}}$每 SIMD 的 lane 宽32
    $f$峰值引擎时钟2.4 GHz
    $W_{\text{stack}}$HBM4 每 stack 接口位宽2,048 bit
    $N_{\text{stack}}$HBM4 stack 数12

    峰值的物理意义只有一条乘法链——单元数 × 每单元每时钟操作数 × 时钟：

    $$\text{Peak} = N_{\text{WGP}} \times \left(\frac{\text{FLOP}}{\text{clk}\cdot\text{WGP}}\right) \times f$$

    4.2 Vector FP32 的 2 倍缺口 —— 两代共有的口径，不是本代新增的坑 #

    规格表给 Matrix/Vector FP32 = 315 TF。按"每 lane 每时钟一个 FMA"算：

    $$256 \times 4 \times 32 \times 2\ \frac{\text{FLOP}}{\text{FMA}} \times 2.4\,\text{GHz} = 157.3\ \text{TFLOP/s}$$

    正好是标称值的一半。反解每 WGP 每时钟的 FP32 吞吐：

    $$\frac{315\ \text{TF}}{256 \times 2.4\,\text{GHz}} = 512\ \frac{\text{FLOP}}{\text{clk}\cdot\text{WGP}} = 2 \times (4 \times 32 \times 2)$$

    也就是说标称峰值要求每 lane 每时钟 2 个 FP32 FMA。ISA 手册里有两条路都能达到

    这个上限，二者通向同一个天花板、不叠加：

    路径opcode代次约束性质
    packedV_PK_FMA_F32 / V_PK_MUL_F32 / V_PK_ADD_F32CDNA 3 起，本代仍然存在数据布局：两个 FP32 要能凑成一对操作数
    VOPD 双发射26 条 V_DUAL_*本代新增调度：编译器要找到两条互相独立、操作数/寄存器 bank 兼容的 VALU 指令

    关键在于这个 2 倍不是本代才引入的假设：前代 Vector FP32 = 157.3 TF 同样出自

    每 CU 256 FLOP/clk ÷ 64 lane（4× SIMD16）= 每 lane 每时钟 2 个 FMA，与本代每 WGP

    512 FLOP/clk ÷ 128 lane 是同一个口径。由此三条结论：

    • FP32 的代际增益（157.3 → 315 TF）全部来自向量 lane 翻倍（16,384 → 32,768

      • lane），没有任何新指令的贡献。

    • 既不能 pack、也不能配对的 FP32 代码只能拿到一半峰值（157 TF），**但这在 MI355X

      • 上同样成立**——移植不会让情况变差，它不是本代新增的陷阱，而是读这一行规格时

      两代通用的口径问题。

    • VOPD 的真实价值不在头条数字，而在于它为无法表达成 packed pair 的代码提供了

      • 第二条通往同一上限的路：调度路线而非数据布局路线。这是货真价实的新增能力，

      只是与 315 TF 的可达性无关。

    白皮书对 packed 与 dual-issue 两者都没有提过一个字，所以"每 lane 一个 FMA"的朴素

    读法会把 FP32 峰值算少一半。Vector FP16 也是 315 TF，与 FP32 同速，说明向量侧

    没有额外的 FP16 打包收益可用。

    4.4 MXFP6 失去了"免费精度"地位（本篇最高代价的静默变更） #

    升级——这是 CDNA 4 时期最好用的一条量化经验。本代规格表里

    MXFP6 = MXFP8 = 20.13 PF，只有 MXFP4 = 40.26 PF。

    代价，而它相对 MXFP8 不再带来任何速度好处——只省内存足迹与带宽。前代那条

    "MXFP6 是严格甜点"的结论在本代失效：现在的甜点结构是"要吞吐就 MXFP4（且有了

    分数 scale，见 §5.3），要精度就 MXFP8"，MXFP6 被挤成一个只在内存受限时才划算的

    中间档。

    这是本篇对软件影响最大、而白皮书完全没有提示的一处变更：它不体现为任何数字的

    下降（MXFP6 的绝对吞吐仍然翻倍了），只体现为格式之间相对次序的重排，因此

    只看"每一项都涨了"的读者会完全错过它。CDNA 4 时期基于"MXFP6 免费"建立的量化

    配方必须重新评估。

    4.5 HBM4：位宽 3 倍，带宽只有 2.9 倍 #

    接口位宽从 $8 \times 1024 = 8{,}192$ bit 涨到 $12 \times 2048 = 24{,}576$ bit，

    正好 3.0 倍；带宽只有 23.3/8 ≈ 2.91 倍。差额来自每 pin 速率：

    $$R_{\text{pin}} = \frac{23.3\,\text{TB/s} \times 8}{24{,}576\ \text{bit}} \approx 7.59\ \text{Gb/s}$$

    而前代 8 stack × 1024 bit × 8 Gb/s = 8.192 TB/s（AMD 对外写 8 TB/s）。**若本代

    也跑 8 Gb/s，峰值应是 24.58 TB/s。（推导）也就是说 HBM4 这一代是用位宽换

    速率**，per-pin 信号速率相对 HBM3E 略有回退，白皮书只强调"位宽翻倍"而没提这

    一点。这对功耗有利、对延迟中性，但意味着"HBM4 = 更快的 pin"是错误直觉。

    4.6 寄存器堆：容量守恒，AccVGPR 消失 #

    白皮书说 VGPR 重组是"while preserving the overall register file capacity"。

    把三个来源拼起来正好闭合：

    • 图 7（图像转录）：每 SIMD 128 KB vector register。
    • 白皮书：单 wave 可寻址 1,024 reg/thread，前代 MI355X 为 256。
    • ISA 手册：AccVGPR 在 823 页中零出现，累加器寄存器文件不再存在。

    前代每 SIMD 的可寻址寄存器是 256 VGPR + 256 AccVGPR = 512 条 × 64 lane × 4 B =

    128 KB；本代是 1,024 条 × 32 lane × 4 B = 128 KB。**容量确实守恒，代价是

    accumulator 不再有独立寄存器堆**（推导 + ISA 手册）。对 kernel 的直接后果：

    WMMA 的累加器现在与操作数争夺同一个 VGPR 池，前代靠 AccVGPR 免费拿到的一半寄

    存器空间没有了，累加器重的矩阵 kernel 需要重新做寄存器预算。

    另一个反直觉的结论（推导）：每单元驻留 work-item 数没有增加。前代每 SIMD

    8 个 wave64 = 512 个 work-item，本代 16 个 wave32 = 512 个。全片

    $256 \times 4 \times 512 = 524{,}288$ 个 work-item，两代相同。Wave32 的收益是

    粒度（更少的分支分歧浪费、更细的寄存器配额、单周期发射），不是更多的线程级

    并行度——白皮书列的三项收益（instruction latency、branch divergence、register

    pressure）恰好都是粒度收益，措辞是准确的，但"twice as many resident waves"容易

    被误读成 latency-hiding 能力翻倍。

        11. 硬件 → 软件的前向影响 #

        按"因为这代硬件，可以/必须写什么新软件"排列：

        1. 手写矩阵 kernel 必须重写，不是重编译。 MFMA/SMFMAC/AccVGPR 三者同时消失

          2. （ISA 手册），矩阵路径改为 V_WMMA_/V_SWMMAC_，tile 只剩 16×16。

          受影响最重的是按 32×32 MFMA 手工排流水的库（CK、rocBLAS 的汇编内核、

          Triton 的 AMD 后端 lowering、以及一切内联 __builtin_amdgcn_mfma_* 的代码）。

          白皮书那句"exposed to developers through ROCm … without requiring

          application-specific optimizations"对框架用户成立，对写 kernel 的人不成立。

        2. async-first 的 kernel 结构第一次在 CDNA 上可行。 TDM（descriptor 从 SGPR

          3. 加载、异步、多播、LDS↔DRAM 直连）+ GLOBAL_LOAD_ASYNC_TO_LDS_B* +

          CLUSTER_LOAD_ASYNC + 异步 barrier + 最多 16 workgroup 的 cluster

          （ISA 手册），构成一套 producer/consumer 流水的完整原语。这意味着

          Hopper 风格的 warp-specialized GEMM/attention 结构可以移植过来，而 CDNA 4

          上只能用 L1→LDS 直读近似。

        3. FP32 向量代码有两条到达峰值的路，且移植不会变差。 315 TF 需要每 lane 每

          4. 时钟 2 个 FMA，可走 packed（V_PK_FMA_F32，CDNA 3 起，本代仍在）或 VOPD 双

          发射（本代新增）；两者通向同一上限、不叠加，两条都走不通就只有 157 TF——而这

          在 MI355X 上同样成立（§4.2）。本代真正多出来的是一条不依赖数据布局的路：

          凑不成 pair 的两条独立 FMA 链现在可以靠调度配对。

        4. 寄存器预算重做。 1,024 reg/thread 的上限意味着满分配 = 每 SIMD 1 个 wave；

          5. AccVGPR 没了，累加器占用操作数同池（§4.6、§7）。占用率与 tile 大小的

          trade-off 曲线整条移位，auto-tuner 的搜索空间必须重设。

        5. 量化配方要重评（本代对软件影响最大的一条）。 MXFP6 不再与 MXFP4 同速，

          6. 前代 16,384 FLOP/clk/CU 的并列关系被打破（§4.4），"免费的 6 bit"消失；

          反过来 MXFP4 拿到分数 block scale 与 16 元素 block（图 4），FP4 训练从

          "精度不够"变成"值得试"。框架侧需要支持带尾数的 block scale 编码，这不是

          标准 OCP MX E8M0 的编码路径。

        6. FP64 GEMM 需要新的落地方案，而向量路径同时被加强了。 矩阵 FP64 指令消失

          7. （ISA 手册），只剩向量 FP64；依赖 FP64 MFMA 的 HPC 库要么退回向量路径，要么

          走精度补偿算法。值得注意的是 ISA 同代新增了 5 条 FP64 双发射 opcode

          （V_DUAL_FMA_F64 / ADD_F64 / MUL_F64 / MAX_NUM_F64 / MIN_NUM_F64，

          均限于 VOPD3 的 X slot）——矩阵路被删的同一代，向量路拿到了吞吐机制，这读起来

          像是刻意的补偿而非巧合。

        7. 通信库简化，但拓扑假设要改。 split DMA 让 RCCL 一类库不必感知 UALoE 拓扑

          8. （白皮书），同时 72-GPU 单跳全连接使"任意两 GPU 等距"成为可依赖的前提——

          ring/tree 的拓扑感知优化在 pod 内失去意义，all-to-all（MoE expert 路由）成为

          一等公民。跨 pod 仍是 RDMA over Ethernet，两套语义的边界正好落在 pod 边界上。

        8. 部署与调度软件要认识 vPod。 故障隔离单元是 vPod（若干 Compute Tray，

          9. 每 Tray 4 GPU + 1 CPU，图 12），且可能需要 checkpoint 回滚；调度器与

          checkpoint 策略应按 4-GPU 托盘粒度对齐，而不是单 GPU 粒度。

        9. 多租户推理有新的隔离面。 boot 时 1/2/4/8 分区 + SR-IOV + fabric 细分 +

          10. 可选 AES-256-GCM + guest VM 安全域跨 GPU 透明扩展（白皮书），使

          "一个物理机架切给多个租户"在硬件层面成立；但 NPS 停在 2（§8.3）意味着

          CPX 的 8 个分区在内存交织视角上并不各自独立。
