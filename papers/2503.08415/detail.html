TokenSim — 深度解析（L2） #

1. TL;DR #

一个基于 SimPy 离散事件引擎的 LLM 推理系统模拟器：把可插拔的算子级 compute

backend（如 GenZ）与用户可自定义的两级调度器 + 细粒度内存管理器拼在一起，从

真实数据集采样动态请求负载，输出延迟分布与内存时序，对真实 vLLM 部署误差 <1%，

并首次支持 prefill/decode 分离（disaggregation）模拟。

2. Q1 / Q2 / Q3 #

Q1 — 痛点（这篇要解决什么） #

已有 LLM 推理模拟器（GenZ、LLMCompass）把输入限制为单请求或单 batch，只报告

单条 test case 的延迟与内存占用。但真实 serving 面对成百上千并发请求：用户满意度

绑定在尾延迟分布上，内存占用随请求进出动态变化。缺乏 continuous batching /

动态负载支持的模拟器，对真实工作负载给出的指标严重失真（§IV-A 就是用来证明这一点的）。

Vidur 用 random-forest 回归估算算子时间引入额外误差且每次运行前需 ~400s 预训练；

LLMServingSim 慢于实时且难以适配新模型/硬件。没有任何模拟器支持 prefill/decode 分离。

Q2 — 方法（怎么做的） #

TokenSim 用离散事件仿真把推理系统拆成四个可替换模块：

(i) 从数据集 + 参数生成动态请求流的 workload generator；

(ii) 两级调度器（global scheduler 分派请求到 worker，每个 worker 的 local scheduler

在 iteration 之间决定请求去留），二者均为用户自定义函数；

(iii) 任意粒度（block / token / byte）的内存管理器，跨节点组成一个大内存池，并含

一个通信模型按带宽算 KV cache 传输时延；

(iv) 可插拔的 compute simulator（如 GenZ）负责一次 iteration 的算力时间。

核心技术壁垒（THE single hardest-to-replicate insight）：不是任何单一模块，而是

"breakpoint（算子级钩子）+ 两级调度器"这套抽象——它让 disaggregation 这类跨

worker 的 KV cache 迁移只需两行代码即可表达（在模型配置末尾挂 breakpoint：local

scheduler 把带新 token 的请求交回 global scheduler，global scheduler 再派给 decode

设备）。把"调度策略"与"硬件时间模型"彻底解耦、并让前者在算子级别可编程，是让同一个

模拟器覆盖 continuous batching / disaggregation / memory pool 三类异构优化而无需改内核

的关键，也是最难复刻的设计取舍。

Q3 — 结果（验证到什么程度） #

  • 对真实 vLLM v0.6.2（LLaMA2-7B / A100 / 2000 条 ShareGPT 请求，多档 QPS）：throughput

    • 几何平均误差 $0.109\%$；P50 / P99 / max 请求延迟误差 $0.6\%$ / $0.254\%$ / $0.337\%$，

    整体 <1%。延迟 CDF 与真实硬件高度重合（Fig 5）。

  • 对 SOTA 模拟器：精度高于 Vidur 与 LLMServingSim（Table II），且无需 Vidur 的 ~400s

    • 预训练，运行更轻量灵活。

  • 首次验证 disaggregated prefill/decode 模拟（对标 DistServe，2×A100，Fig 7）。
  • 用它跑出 7 条对系统优化的反直觉洞见（§5 展开）。

⚠️ 存疑：Table II 标称"latency percentage difference"，但数值（2.7~13）随请求数单调增长

且各模拟器与"Local 真实硬件"高度接近——更像是总耗时(秒)而非百分比误差，与 §III-C

的 <1% 声明无法调和。这是论文自身未澄清的一处内部矛盾。

3. 架构 / 方法图 #

Paper's Figure 1（caption: "TokenSim system overview."）。 系统运行在一个跟踪全体

worker 仿真时间的 inference loop 中：workload 从数据集+参数生成 → dispatcher 交给

global scheduler → 按用户设定分派到各 worker。每个 worker 并发运行，由 **local

scheduler（多种算法）驱动，并与监控设备内存利用率的 memory manager** 协作。一旦

scheduler 为某次 iteration 组好 batch，就把信息送给 compute simulator（如 GenZ） 求

iteration 时间；发生跨设备数据搬运时，communication model 依网络参数连接 memory

manager 计算传输时延。读者应注意：compute backend 是可换的插槽，这正是它能覆盖多种硬件

配置的原因。

Paper's Figure 2（caption: "One example of TokenSim configurations."）。 配置文件是用户

表达 global/local scheduler、模型结构与 breakpoint 的地方——把调度策略当配置而非内核代码，

是这套模拟器"可扩展"的落点。

*Paper's Figure 3（caption: "User-defined scheduler example ... defining a disaggregated

architecture."）。* 展示 global + local scheduler 两个用户函数如何配合：global scheduler

可访问当前 worker 数、硬件类型、并发请求数，且可有状态（记录每 worker 已派请求数以做

load-aware 调度）；local scheduler 访问当前任务队列与内存利用率。disaggregation 正是靠在

模型配置末尾挂 breakpoint、两行代码把请求在 prefill/decode worker 间转交实现的。

原文没有单独的时序图，这里用 Mermaid 补上调度决策与 KV 迁移的先后关系（结构信息，

raster 图未覆盖）：

Scheduler 作为一等公民：queueing discipline 由用户函数决定（可实现 FCFS / load-aware

/ SLO-aware），batching 决策发生在每次 iteration 之间（continuous batching 语义）。

内存管理器与调度器分离：分配单元可为 block / token / byte，KV cache 传输走独立的

communication model。跨节点通信：由 memory bandwidth 参数化，支持顺序与并发（预加载

buffer）两种 overlap 模式。

4. 作者证明 #

无形式化作者证明 — 仅实证。

这是一篇模拟器系统论文，没有吞吐/延迟闭式模型，也没有 notation table、单调性或凸性证明。

其"正确性"完全由实测对齐支撑：对 vLLM、Vidur、LLMServingSim、DistServe 的误差实验。

框架论文常见的 performance model（λ, μ, B, T_M, N_p 等）在此缺席。

一个形式化模型若存在，本可澄清的几处（记为"模型本应回答但论文未回答"）：

  1. §V 的 $2\times 312$ 算力阈值——decode 能力上限的来源无推导、无单位、无硬件语境；一个

    2. roofline 式模型（compute vs. HBM BW 的 min 关系）本可给出这个拐点的物理意义（312 恰为

    A100 fp16 TFLOPS，疑似 2 张 prefill 卡的累计算力，但论文未点明）。

  2. §IV-E memory cache 在 $\leq 32$ token 输出下收益递减、~64 token 达峰的阈值机制未给模型；

    3. 一个"检索 800ns/block 固定开销 vs. 重算节省"的收支模型本可解释 32 这个转折点。

  3. §IV-C1 "prefill/decode 最优比主要取决于 output length"——若有排队论/吞吐模型，可判定

    4. 最优是内点还是边界解，以及 input length 的二阶作用为何被降级为"primarily"的次要项。

    粗核——预算 5 张 A100 时，1×A100(prefill) + 7×G6-Aim(decode) 吞吐 $29.1$ vs.

    代码公开：https://github.com/pku-lemonade/TokenSim（论文 §0 Para 2）。L1 未抓取具体

    file:line，故以下为架构级指引而非行号引用；需精确定位时应回到该 repo 核对。

    • 离散事件引擎：SimPy 4.1.1（ref [21]）——active component（worker/device）注册进

      • environment，仿真时间由事件推进；可在无 GPU 的个人电脑上跑。

    • compute backend 插槽：GenZ（ref [10]）作为默认 iteration-time 后端，接口设计为可换

      • （§III Para 3 "supports diverse compute simulators"）。[实现未公开具体接口签名]

    • breakpoint 机制（关键实现细节 1）：在模型配置文件末尾追加算子级 hook；默认

      • breakpoint 在每 token 生成后触发调度器。disaggregation 只需两条 hook：local scheduler

      把带新 token 的请求交回 global scheduler、global scheduler 派往 decode 设备（§III-A

      Para 3–4）。这是"两行代码实现分离"这一卖点的落地点，易被忽略。

    • 通信模型（关键实现细节 2）：输入 = cache 位置(host/device) + 数据大小 + 带宽，输出 =

      • 传输时间；靠 SimPy 事件驱动支持 sequential 与 concurrent（预加载 buffer）两种 overlap，

      调大 buffer 可逼近 ideal multi-preloading（§III-B Para 4–5）。多轮缓存实验中检索时延取

      固定 800 ns/block（ref [18]，§IV-E），无敏感性分析——移植时需自行参数化。

    • 内存管理粒度：block / token / byte 三种可选，跨节点内存组成统一内存池（§III-B）。

    核心技术壁垒（§7 专段）：最难复刻的不是任一模块，而是让"调度策略"以**算子级

    breakpoint + 两级 scheduler**的形式与"硬件时间模型（compute backend）"完全解耦的抽象层。

    正因调度是用户函数而非内核逻辑，同一引擎才能在不改内核的前提下表达 continuous batching、

    prefill/decode 分离、以及 multi-round memory pool 三类结构迥异的优化；复刻者即便照抄

    SimPy loop，也要重新发明这套"配置即策略、breakpoint 即迁移点"的接口契约，才能达到相同的

    可扩展性与 <1% 的对齐精度。

    8. Deployment context（实践上下文） #

    • serving stage：编排/仿真层——不真正跑 kernel，而是给 prefill-only / decode-only /

      • both / 分离编排各档配置估性能；对低到高并发均可（案例用到 50,000 并发请求采样）。

    • hardware affinity：结论层面，decode 亲和高带宽/高容量（PIM 如 G6-Aim 划算），prefill

      • 亲和高算力（容量/带宽过剩）；工具本身无 GPU 亦可运行（SimPy 纯 CPU）。

    • ecosystem integration：不是插进 vLLM/SGLang 的执行器，而是独立模拟器，以 GenZ 类

      • compute backend 为可换插槽；把真实系统（vLLM v0.6.2 / DistServe）当对照真值来校准。

    • migration path：跑 vLLM 的团队采用它不是替换 runtime，而是把它当**离线 what-if 探索

      • 器**——改配置文件里的 scheduler/内存策略/硬件参数，无需真机即可预演分离比、PIM 替代、

      prefill 内存下调等决策；成本是重写 compute backend 适配自家硬件的算子时间模型。

    §12 软→硬反向启示：TokenSim 是纯软件模拟框架（不做 megakernel / cache-scope 控制 / chiplet 亲和），不触发硬件反向启示条款。其结论对硬件的间接暗示（decode 适配 PIM、 prefill 算力主导）属于被模拟系统的性质，而非模拟器自身的硬件诉求。
