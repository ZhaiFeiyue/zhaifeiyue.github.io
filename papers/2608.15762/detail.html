SliceScheduler：全局仿真引导的算子级动态调度 #

1. TL;DR #

容器调度无法回收服务内部秒级空闲片段。SliceScheduler 把调度单元下沉到"算子"（实测粒度=融合 8 层的 LLM layer），用带 shape 的全局映射图 GMG 重建集群一致快照，再以事件驱动仿真器做 what-if 打分选放置：token 吞吐 1.10–2.29×，SLO 达成 98.9%，运行时开销 0.0%。

2. Q1 / Q2 / Q3 #

Q1 — 痛点：空闲片段的"所有权"与"控制粒度"双重错配 #

作者从一家工业公司的 AI coding 服务取两周 trace，选四个代表日回放。单张 A16 上跑 Llama3-8B 实例，平均 GPU 利用率 64.0%，其余时间被切成大量短片段：p50 2551.11 ms、p90 10887.64 ms、p99 17790.31 ms，且短于 p99 的片段占总空闲时间的 95.6%。

论文 Figure 1，原始 caption："CDF of idle-slice durations from replaying a production AI coding traces on a single-GPU model instances. Only idle slices longer than 10 ms and less than 20 s are included. Average GPU utilization is 64.0%, and idle slices shorter than p99 account for 95.6% of total idle time."

这张图是全文的立论基础，读者要看的是曲线的陡度：横轴只画 90%–100% 的空闲片段计数区间，纵轴 CDF 已经从 0 爬到 1，意味着绝大多数空闲时间由数量占比极小、但每段都只有秒级的片段构成。这个形状直接排掉了"扩缩容能解决"的可能——秒级窗口装不下分钟级的重调度。

论文把失败原因拆成两条正交的轴：

  1. 控制粒度太粗（§2.2.1）。容器编排本来是为部署设计的，调度器选完节点后由应用进程驱动 GPU，调度器不再直接控制计算单元和显存。弹性机制要走 checkpoint → 重排队 → gang scheduling 等待 → 拉镜像 → 环境初始化 → checkpoint 加载，端到端"on the order of minutes"。用分钟级机制去填秒级洞是无效的。
  2. 资源所有权独占（§2.2.2）。空闲片段在账面上仍属于原容器，而用户应用不可修改，无法指望它主动让出。静态空间切分（MIG 类）只能拿到固定份额，抓不到执行期间动态产生的瞬时片段；不做静态切分的共享（MPS / AntMan 类）在 LLM 场景下更难，因为权重和运行时状态常驻显存，峰值期直接变成内存压力和干扰。

    3. 真正把问题钉死的是一个测量：把四个代表日 trace 回放在四个模型实例上，跨 GPU 的空闲时间重叠不超过 20%。这条数据的杀伤力在于它否定了"扩大共享作用域"这条退路——低优先级作业需要覆盖的 GPU 越多，这些 GPU 同时空闲的概率越低。于是低优作业若仍以 GPU-sharing 容器形态部署，就必须等多张卡同时可用才能推进端到端计算。要吃掉散落的碎片，低优作业本身必须可被细粒度分解并跨容器边界铺开。

    一个 1 GPU 上的可行性探针（Fig 3，两个 Llama3-8B 实例，一个高优在线、一个低优离线）显示：机会式填洞在 SLA 不破的前提下把 token 吞吐提到 $1.25\times$。所以机会存在，缺的是抓取它的抽象。

    Q2 — 方法：把"集群状态"做成可克隆、可仿真的对象 #

    系统范围先说清楚：这是推理服务（serving）+ 训练图仿真验证混合的调度层，覆盖 prefill 与 decode 两个阶段但不改动批处理逻辑本身——它不是 continuous batching 的替代品，而是坐在其下方接管算子到加速器的映射。并行维度上它只拥有"图切分 + 算子放置"这一轴（候选划分是预定义的加速器 partition 集合，等效于 PP / 层间切分），TP / EP / DP 全部交给被调度的图自己表达。部署形态是单机多卡集中式 master：实测 8×A16 在一台服务器内，跨节点从未验证。

    四层闭环：

    • GMG（Global Mapping Graph）：Shape DAG + Accelerator Set。每个节点是一个带 tensor shape 与执行状态（unscheduled / issued / done）的算子，边是数据依赖，节点映射到加速器集合。计算模式是 register-once / instantiate-many：应用先注册带符号 shape 的图模板，之后反复实例化，SliceScheduler 从输入 shape 推断实例中每个算子的 shape。四类调度元数据挂在 GMG 上：每算子的性能 estimator、全局与逐节点时间戳、输出 tensor shape、以及标记哪些中间结果被持久保留的 checkpoint 元数据。
    • 全局仿真器：两个线性 estimator（传输 = 仿射 size 模型，算子 = shape 特征基）+ 事件驱动推进。构造阶段从 GMG 快照反推每张卡的队列内容、当前执行算子、以及显存驻留集合；推进阶段每步取最早完成的算子作为事件、推进统一仿真时间线、级联启动同队列中就绪的后继。
    • 调度模块：GMG 上维护 scheduled / unscheduled 两个 frontier 界定增量边界。每轮从 unscheduled frontier 取最高优先级算子，沿后继收集一个小的连通批次，对预定义候选 partition 并行做 what-if 仿真，丢弃 OOM 候选，选仿真平均完成时间最小者。
    • 算子执行器：每卡一个依赖驱动（而非发射顺序驱动）队列，一次只跑一个算子；跨卡传输被分解为 Intent / Recv / Send 三个算子，由 master 在一张独立的通信图上做仲裁。

    核心技术壁垒：不是任何单个组件，而是 "GMG 快照 ≡ 集群一致快照"这条可重建性不变量，以及维持它的三个耦合约束。仿真器之所以能只从 GMG 就推出"哪个算子正在跑、显存里有哪些 tensor"，靠的是三件事必须同时成立：(i) 每队列一次只执行一个算子（§3.5.1 的硬不变量）；(ii) 就绪定义为"所有前驱 done 且其输出已在本地 HBM"，从而当前执行算子唯一确定为 ready time 最早的 issued 算子；(iii) shape 在执行前可推断，于是显存占用可在放置前算出。任何放松——异步多流、动态 shape、投机执行、乱序队列——都会同时打破状态可重建性和显存安全性判定。复制这个系统的难点在于同时守住这三条，而不是写出仿真循环。

    论文 Figure 4，原始 caption 节选："The system centers on the Global Mapping Graph (GMG) ... Runtime feedback continuously updates GMG and estimators, enabling a closed-loop, prediction-driven scheduling system."

    图中要注意的是箭头的方向构成一个闭环而非流水线：GMG 在中心，仿真器、调度模块、执行器围绕它，编号边 (1) 注册与实例化 → (2) 调度与仿真 → (3) 发射 → (4) 传输仲裁 → (5) 反馈回到 GMG 与 estimator。反馈边是关键——estimator 在线细化正是论文归因自己比 SimAI 精确一个量级的原因（§5.4.2）。

    论文 Figure 5，原始 caption："GMG maps operators to accelerators. It describes the global status of tasks and the cluster, as well as the computation progress of all tasks."

    左侧 Shape DAG 与右侧 Accelerator Set 之间的映射边就是调度决策的物化形式。读者应注意 GMG 同时承载了三类信息——计算结构、放置、执行进度——正是这个"三合一"让克隆 GMG 就等于克隆整个集群的可仿真状态。

    论文 Figure 6，原始 caption："An example of the construction and simulation of the global simulator."

    这张图把仿真拆成必须分开理解的两步：左半是构造——从 GMG 快照反推每张卡的算子与依赖，为每卡建一个仿真队列；右半是推进——沿统一仿真时间线逐事件前进。构造步才是难点所在（它依赖 §4 讨论的可重建性不变量），推进步只是标准的最早完成事件循环。

    下面的时序图把请求生命周期与两个 first-class 组件（调度器、显存视图）显式分开，这是 Figure 4 的框图无法表达的结构：

    排队纪律值得单列：批次收集是优先级驱动的（highest-priority first），但放置选择是仿真分数驱动的（min predicted average completion time）。这两级的组合产生了论文声称的三个"涌现"性质——局部性、SLA 优先、负载均衡——下面 §6 会逐条检查这个因果链。

    显存管理器在论文中不是独立组件，而是仿真器的一个推断能力：分配单位是算子的输出 tensor（不是 page，不是 block），生命周期由"就绪 + 执行中"算子集合隐式决定，回收发生在算子标记 done 时释放资源账目。没有 eviction 策略，没有 swap to CPU/disk，没有碎片整理——准入控制完全前置为"仿真出 OOM 的候选放置直接丢弃"。这是一个纯 admission-time 的显存安全模型，代价是无法处理运行期意外增长。

    论文 Figure 7，原始 caption："An example of a computation graph partition and accelerator assignment. 'Compute' refs to as 'Comp'."

    图中每张卡的队列里混排着 Comp 节点与跨卡传输节点——这是"把传输当作普通算子入队、再由仲裁门控其执行"这一设计选择的直接可视化，也是为什么传输延迟能自然进入仿真时间线（见 §6 第 3 步）。

    4. 作者证明 #

    论文有三个形式化对象：两个 estimator（Eq 1 / Eq 2）和一个可扩展性模型（Eq 3）。没有关于 GMG 一致性或仲裁无死锁的形式化证明——这两条都是断言。

    方程与物理意义 #

    Eq 1（传输延迟）：$t = \alpha \cdot size + c$

    标准的 latency–bandwidth 仿射模型。关键设计是按加速器对而非全局拟合，因为有效带宽取决于链路（NVLink vs PCIe 跳数）；截距 $c$ 让小 tensor 传输不免费，而这正是调度器局部性惩罚的来源——破坏局部性的放置会把这些传输项加进仿真时间线，抬高下游算子的预测完成时间。

    Eq 2（算子执行时间，以 batched matmul 为例）：$t = \beta_{1}(bmnk) + \beta_{2}(bmk) + \beta_{3}(bkn) + \beta_{4}(bmn) + \beta_{5}$

    这是手工设计的特征基而非黑盒回归：一个 FLOP 项（$bmnk$）+ 三个数据搬运项（两个输入 tensor 大小 $bmk$、$bkn$，输出 tensor 大小 $bmn$）+ 一个截距。为什么用这个形式而不是纯 roofline？因为 roofline 需要知道算子是 compute-bound 还是 memory-bound；这里的线性组合让拟合过程自己决定哪一项主导，同时保持"线性于特征"从而可在线廉价重拟合、并以仿真速度求值。它按 (加速器类型, 模板算子) 对维护，而非按算子种类——这是为了吸收同一算子在不同层位置上的实现差异。

    Eq 3（调度及时性）：$t = \dfrac{N l + 1}{s g}$

    分子 $Nl + 1$ 计一轮的仿真工作量：视界 $l$ 要在全部 $N$ 张卡上推进，加上批次本身（$+1$）。分母 $sg$ 是集群自身执行"买来"的仿真预算：每算子 $g$ ms 真实执行时间，乘以 $s$ 算子/ms 的仿真速度。

    六项最小检查 #

    1. 量纲一致性 — 通过（但需注意 $l$ 是无量纲的）。分母 $s g$ = (算子/ms)·(ms) = 算子，分子若 $l$ 无量纲则 $Nl+1$ 亦为算子计数，$t$ 无量纲，符合"比值"定义。这只在 $l$ 已被 scheduling volume 归一化的前提下成立——也就是说 $v$ 是被吸进 $l$ 的量纲因子。论文没有明说这一点，但这是唯一能让 Eq 3 量纲自洽的读法。
    2. 一阶数值复现 — 通过。$g = 42.3 / 4 = 10.575$（Llama3-8B 的 32 层每 8 层融合为一算子，故一次前向 4 个算子，平均 decode 延迟 42.3 ms）。代入 $s = 176.8$、$l = 3$、$t = 0.1$：$N = (t s g - 1)/l = (0.1 \times 176.8 \times 10.575 - 1)/3 = (186.96 - 1)/3 = 61.99$。论文报 $N \approx 62$ → "about 64 GPUs"。数字确实是算出来的，不是 sweep-then-fit。
    3. 单调性与边界 — 通过，且最优解在边界。$\partial t / \partial N > 0$、$\partial t / \partial l > 0$、$\partial t / \partial g < 0$、$\partial t / \partial s < 0$，全部严格单调，无内点极值。这意味着决策质量与及时性之间不存在解析最优点，只有一条约束线 $t \leq t_{\text{target}}$；实践中只能把 $l$ 和 $g$ 往"更粗"推到约束边界。这解释了 §5.1 为什么把层融合成调度单元而不用 ATen op——若用 ATen op，$g$ 会小 2–3 个数量级，$N$ 的上限随之崩到个位数。
    4. 各项能否被排除 — 一处未通过。声明的 $v$ 完全不进公式，而 §5.5 又说"我们离线调 $v$ 和 $l$"。若 $v$ 已被 $l$ 的归一化吸收（第 1 项的读法），那"同时调 $v$ 和 $l$"就是同一自由度调两次；若没有被吸收，公式缺项。论文两处表述不能同时为真。
    5. 模型与实测交叉验证 — 未通过（模型层面）。Eq 3 从未在变化的 $N$ 上被测量验证：全部实验在单机 8 张 A16 上完成，而 64-GPU 的适用性结论是纯纸面外推。作为 framework 论文的核心定位是"cluster-wide"，却没有任何跨节点实验——集中式 master 的反馈延迟、状态陈旧、真实执行偏离仿真重建状态时的行为，全部未建模也未测量。
    6. 实验数字自洽性 — 通过。Fig 8 的柱标签能反推论文声明的区间：token 吞吐 $18.51/16.82 = 1.10\times$、$18.51/8.08 = 2.29\times$，匹配摘要的 "1.10–2.29×"；request 吞吐 $1.23/1.12 = 1.10\times$、$1.23/0.54 = 2.28\times$，匹配 "9%–129%"。但有两处口径漂移需记录：(a) 摘要说 "maintaining SLA violations within 9%"，§5.2 说 "improves SLO attainment by about 9%"——一个是违约率上界、一个是提升幅度，Fig 8(c) 支持后者（98.9% 即约 1.1% 违约）；(b) §5.4.3 的 176.8 / 0.065 = 2720×，是约 3.4 个数量级，论文两处都写"about four orders of magnitude"。

      7. 未被证明的两条：GMG 与集群一致快照的等价性（§3.3.2 仅给出重建论证，无证明、无测量）；传输仲裁的无死锁性（§3.5.2 声称避免死锁，但冲突无关边集的选择算法未给出——文字暗示一个匹配问题——既无形式论证也无压力实验）。

      5. 实验与数据 #

      平台：单台服务器，2×Intel Xeon Platinum 8468（96 核）、1600 GB 主存、8×NVIDIA A16（各 64 GB）。在线负载是 §2.1 四条一日 trace 的 19:00–19:30 片段；离线负载每秒一请求、输入 2048 token、固定输出 15 token。调度单元 = 融合后的 LLM layer。

      基线全部由作者自行实现（理由是 GPU 共享系统"并非总是公开可得"）：Static-Online（容器级 pinning，四实例分别钉在 GPU 对 (0,1)/(2,3)/(4,5)/(6,7)）、Subset-Share（对 AntMan 的优先级感知共享建模，离线实例限定 4 卡子集）、Dual-Share（对 Orion 的干扰感知共享建模，两个离线实例分居两个 4 卡子集）、Full-Share（单个离线实例跨全部 8 卡）。

      5.1 端到端协同放置 #

      论文 Figure 8，原始 caption："Performance comparison of SliceScheduler and baselines."

      四个子图的排序模式高度一致：Static-Online < Full-Share < Subset-Share < Dual-Share < SliceScheduler，说明"共享作用域越灵活收益越高"这条趋势在吞吐和利用率上成立。但真正的分水岭在 (c)：三个共享基线的 SLO 达成全部落在 89.9%–90.7% 的 0.8 个百分点带内，SliceScheduler 跳到 98.9%。读者应注意 SLO 阈值被定义为 Static-Online 的 p90 TTFT，所以 Static-Online 的 90.0% 是定义上近乎固定的；三个共享基线在多背了 1–2 个离线实例的情况下仍精确聚在同一值，是一个偏紧的巧合。

      绝对量级也需要放在心上：整台 8 卡服务器只有 8.08–18.51 output tok/s、0.54–1.23 req/s。A16 是面向推理/VDI 的 GDDR6 卡，不是数据中心 LLM 服务 GPU，而论文的论述框架（HBM 占用、OOM、权重常驻 HBM）是 HBM 中心的。

      5.3 仿真器端到端精度与速度 #

      论文 Table 2，原始 caption："Average training time per one iteration of Llama3-8B on dual GPUs and simulation error rate." 实测 1.910 s；本文仿真器 1.945 s（误差 1.83%）；SimAI 1.517 s（误差 20.58%）。

      核心技术壁垒（展开） #

      最难复制的不是 GMG 数据结构，也不是事件驱动仿真循环——两者都是标准工程。壁垒是让"GMG 快照可无损重建集群运行态"这条不变量在真实运行时里持续成立。它要求执行器放弃几乎所有现代 GPU 运行时的性能手段：每队列一次只跑一个算子（不能多流并发），依赖驱动而非发射顺序（不能乱序或投机），跨卡传输必须先 Recv 后 Send 且由中心仲裁门控（不能让队列自主发起 P2P，因为原语阻塞、不可抢占、send/recv 错序会形成循环等待），shape 必须执行前可推断（不能有动态 shape）。任何一条放松，仿真器就无法从快照唯一确定"当前在跑哪个算子、显存里有什么"，随之崩塌的是显存安全判定（OOM 过滤是准入期的唯一防线）与完成时间预测（调度的唯一目标函数）。

      有意思的是这套约束反而是它开销为 0.0% 的原因：因为它本来就不做重叠、不做投机，接管调度并未剥夺任何既有优化。代价在别处——它无法与依赖异步流水的高性能 serving 引擎共存。这也解释了为什么论文的基线是 AntMan / Orion 这类共享系统而非 vLLM / SGLang：它不与后者竞争同一层，也不能直接叠加在后者之上。

      关键实现细节（易漏） #

      1. 层融合的数量级不是调参而是可行性前提。§5.1 把每 8 层 Llama3-8B 合成一个算子，得 $g = 10.575$ ms。若按原始 ATen op 调度（单次图执行数千到数万 op），$g$ 落到 μs 量级，Eq 3 的 $N$ 上限直接崩到个位数。融合比例是把系统从"不可行"推到"64 卡可行"的那个旋钮，但论文只说"empirically grouping"，未给敏感性分析。
      2. 候选放置来自预定义 partition 集合，不是搜索出来的。§3.4.2 明确：每个图模板到每个候选 partition 的算子映射也是预定义的（依据是"推理图规则可分解"）。所以决策空间远小于"算子级调度"字面暗示的规模。论文从未说明候选 partition 有多少个、如何选出、并行 what-if 成本如何随该数量增长——而这个计数直接乘在 Eq 3 假定的每轮仿真工作量上，是该模型未表达的第二个自由度（另一个是 §4 检查 4 指出的 $v$）。
      3. Recv-before-Send 的真正理由是重试语义。§3.5.2：目的端 buffer 分配可能临时失败并需重试，故先激活目的端 Recv、成功后才触发源端 Send，让发送方只在目的端就绪时才调用通信原语。这个顺序不是性能优化，而是把"分配失败"从不可恢复的阻塞态转成可重试态。
      4. checkpoint 元数据是增量调度的载体。GMG 每个节点记录哪些中间结果被持久保留在何处（如某卡 HBM），scheduled frontier 由此成为"驻留在加速器上供后续调度接续的检查点"。新图实例可挂接到保留的中间态上——这是多轮对话/前缀复用在该抽象下的表达方式，但论文未把它与前缀缓存的收益关联，也未测量其显存占用代价。

        5. 硬件反向含义 #

        这个框架是硬件贴近型的（显存物理占用建模、互连感知的传输仲裁、跨卡放置），其复杂度反过来指向两个硬件缺口。其一，显存安全只能靠准入期仿真预测，因为 HBM 没有"分配即失败可恢复"的廉价原语，也没有硬件级的 per-context 显存配额与超额通知——如果有，OOM 过滤就不必前置到调度器里，仲裁的 Recv 重试逻辑也可以简化。其二，"每队列一次一算子"这条为了状态可重建而付出的代价，本质上是因为 GPU 缺少可被外部观测的、确定性的队列执行状态导出接口；若运行时能暴露一个廉价的一致执行快照（当前 SM 上算子 ID + 显存驻留集），GMG 的整套重建论证就无需成立，多流并发也可以同时保留。
