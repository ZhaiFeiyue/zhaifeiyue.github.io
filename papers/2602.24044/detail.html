Data-Driven Optimization of GPU efficiency for Distributed LLM–Adapter Serving #

§1 TL;DR #

给定可预测的 LoRA 工作负载（adapter 数量/尺寸/到达率），用 Digital Twin 生成数据训练 ML 代理模型，再用 FFD 变体贪心算法求解 adapter→GPU 放置与每卡 A_max，把每张卡压到"不饿死的最大吞吐点" Max_pack。4 卡实测平均少用 2.4 张 GPU（60%），代价是 ITL 变差。

系统边界：单节点 4×H100，每 GPU 一个独立 vLLM 实例，请求按 adapter 归属路由。没有任何跨 GPU 集合通信——这是一个"把 GPU 当 bin 来装 adapter"的容量规划问题，不是 fabric 问题。

§2 Q1 / Q2 / Q3 #

Q1 — 痛点：Max_pack 是一个位置不定、越界即崩的悬崖 #

多租户 LoRA 服务把成百上千个 adapter 塞在同一个 backbone 上。单个 adapter 的到达率太低喂不饱 GPU，所以要"堆"；但堆过头就越过一个临界点：adapter 权重挤占 KV cache 的显存，batch 装不下，请求积压速度超过处理速度，进入 request starvation（延迟单调发散）。这个最优堆叠点论文记作 $Max_{pack}$，操作性定义是"吞吐仍高于总入向 token 速率 90% 的最高实测吞吐"。

论文 Figure 1（caption: "Throughput as a function of the number of served adapters under varying adapter sizes (left), arrival rates (center) and configured $A_{max}$ (right)."）。

三个面板给出的形状一致：吞吐先近线性上升，越过某点后饱和或下跌。关键在于拐点位置随三个参数剧烈漂移——大 adapter 拐点更早（占显存又增算力），低到达率拐点吞吐更低（要堆更多 adapter 才饱和，adapter 开销累积），而 A_max 本身是双刃：A_max=320 预留显存过多，A_max=96 又限制并行度。图中的叉号是硬 OOM：把 A_max 直接设成 adapter 总数（最"自然"的配置）在大 adapter + 低到达率时直接把权重区开爆。

vLLM 的机制约束放大了这个问题：显存在初始化时静态切分，A_max 决定预留给 adapter 权重的区域大小，且每个槽位按统一上限 $S_{max}$ 分配——不管实际 adapter rank 多大，全按场景中最大的那个算。所以一个 rank-32 的 adapter 会把同卡上所有 rank-8 adapter 的槽位一起撑大 4 倍。

Q2 — 方法：DT → ML 蒸馏 → 贪心装箱 #

三级流水线：

论文 Figure 2（caption: "Proposed data-driven pipeline to address the adapter caching problem (right), shown alongside its expected usage within a production system (left)."）。

左半是生产集成方式：周期性地用"预期下一时段负载"重新调用流水线；右半是流水线内部。注意关键的分工——DT 只在离线跑（生成训练数据），在线决策路径上只有 ML 模型，因为贪心算法要在一次放置里反复查询上千次，DT 的 39 秒量级完全不可用。

  1. Digital Twin（§5）：不是性能公式拟合器，而是把 vLLM 的 continuous batching 主循环用代码重实现一遍，状态转移函数逐步推进（注入到达 → scheduler 更新 batch → adapter cache 换入换出 → model forward）。耗时任务不真跑，改由 4 个拟合估计器给时间。纯 CPU、单核、~200MB。
  2. ML 阶段（§6）：在 DT 生成的数据上训两个头——吞吐回归 + starvation 二分类。特征只有 7 维：adapter 数 $A$、到达率之和与标准差、adapter 尺寸的 max/mean/std、配置的 $A_{max}$。可选 refinement 把 RF 蒸馏成一棵浅决策树，再用 Numba 重写。
  3. 贪心算法（§7）：First-Fit Decreasing 变体。adapter 先按尺寸降序分组（防止后来者抬高 $S_{max}$），组内按到达率 zigzag（高低交替）排列；逐个 provisional 塞进 GPU，到达预设测试点 [8, 16, 32, 64, 96, 128, 160, 192, 256, 320, 384] 时调 TestAllocation 查 ML：先在当前 $A_{max}$ 和下一候选值之间选吞吐更高的，再用 starvation 分类器验一次；不过就整批回滚重排队。

    4. 核心技术壁垒：不是 DT，也不是 ML，而是把 A_max 从"用户拍脑袋的启动参数"提升为与放置决策联合求解的决策变量，并用一个学出来的 starvation 分类器作为可行性 oracle。两个 baseline（dLoRA、LoRAServe）都把 A_max 设成"每卡 adapter 数"——这恰好是 §2.3 已证明会触发 OOM 的配置。整篇论文的优势有相当一部分是从这个联合搜索里榨出来的，而它能成立的前提是有一个足够便宜（0.25ms）又足够准（macro-F1 0.95–0.99）的 starvation 预测器；这个预测器又只能由 DT 喂数据训出来，因为真机穷举一小时一个点根本跑不完。这条"便宜的可行性 oracle"链条是最难复制的部分。

    拓扑层面必须说清楚的事实：节点数 = 1，GPU/node = 4，没有 NIC、没有交换机层级、没有 rail、没有 over-subscription。四张 H100 之间不做任何 tensor/pipeline 并行，也不跑 all-reduce——每张卡是一个完全独立的 vLLM 实例，"分布式"仅指请求按 adapter 归属被路由到不同实例。唯一的数据通路是 CPU RAM ↔ GPU 的 adapter 权重换入换出（PCIe），disk→CPU 被当作一次性初始化成本剔除。因此本文对 fabric、拥塞控制、集合通信算法均无贡献，也不应按这些维度评价它；它在集群语境下的贡献是容量规划 / bin packing 侧：用多少张卡承载给定的 adapter 负载。

    节点内 NUMA / PCIe 拓扑（哪些 GPU 共享 root complex）论文未披露，而这对 adapter 换入带宽是有影响的——见 §4 检查 6。

    §4 作者证明 #

    论文的形式化内容集中在 Eq. (1)（DT 的四个估计器）与 Algorithm 1/2（放置过程）。没有定理，没有最优性/近似比证明——NP-hard 只是引用 bin packing 文献的一句断言，贪心算法的近似质量完全靠实验支撑。

    4.2 Eq. (1) 逐行物理意义 #

    $$Mem_{max}(A_{max}, S_{max}) = T_{max}$$

    纯经验查表，不是闭式解。它只依赖两个静态显存切分旋钮——这与 vLLM 在初始化时预分配 adapter 区域的语义严格一致：一旦 $A_{max}$、$S_{max}$ 选定，token 预算就冻结了。论文承认可以推解析式但"经验拟合更直接且同样准"，未给消融。

    $$Lat_{sched}(B, R_P, A_B, A) = K_1 B + K_2 R_P + K_3 R_P \frac{A_B}{A}$$

    三项一一对应 vLLM 调度器里的三段循环：遍历活跃 batch 检测完成请求（$K_1B$）、部分遍历 pending 队列判定可纳入性（$K_2R_P$）、以及 §5.1.4 那个病态项。第三项的建模选择值得停下来看：分数 $A_B/A$ 表示"已在 batch 中的 adapter 占服务总数的比例"，它刻画的是调度器要扫多深才能找到可执行请求。

    $$Lat_{model}(B, A) = Lat_{backbone} \cdot Overhead_A = (K_4 B + K_5)(K_6 A + K_7)$$

    注意这是乘积不是求和。线性于 $B$ 的因子是 backbone 成本，线性于 $A$ 的因子是相对慢化率——与 Fig. 5 把 adapter 影响报成"相对 backbone-only 的 throughput slowdown / ITL overhead"这一测量方式匹配。截距 $K_5$ 吸收固定每步开销，$K_7$ 吸收 0→1 个 adapter 那个陡降。

    4.3 最小检查集 #

    检查 1 — Eq. (1) 建模形式与测量语义的一致性（通过，但有张力）。 §5.1.2 用语是 adapter 引入"额外的计算与 GPU 内部传输"，直觉上应是加法项；Eq. (1) 却写成乘法。乘法形式在量纲上自洽（$Overhead_A$ 无量纲），且与 Fig. 5 的相对度量口径一致。但它隐含一个物理主张：adapter 开销正比于 backbone 时间，因而随 batch size 增长而放大。这在 backbone 与 adapter 计算共享同一 GEMM 批次时说得通，作为可证伪预测应当能在固定 $A$、扫 $B$ 时验证——论文未做这个正交实验。

    检查 2 — DT 加速比算术（通过）。 Table 2 给 Llama $38.94 \pm 5.58$ s，真机每配置跑 1 小时。$3600/38.94 = 92.4$，$3600/(38.94{+}5.58) = 80.9$。"up to 90×"与均值一致，且下界（含 1σ）仍在 80× 量级。CPU 89.5% 说明确为单核。

    检查 3 — 60% GPU 削减的算术（通过，但口径需注意）。 baseline 恒用满 4 卡，$2.4/4 = 60\%$。但 2.4 是跨所有评测场景的平均值，包含了 Proposed 只用 2 卡的低负载点和用满 4 卡的高负载点；它不是任一具体场景的削减率。论文正文的例子（Qwen 最右配置：256 / 768 adapter 分别用 2 / 3 卡）对应 50% / 25%，都低于 60%，说明 60% 的均值由更极端的低负载场景拉高。

    检查 4 — 显存预算推导，独立复现 "$A_{max} > 144$ 有害" 这个决策树阈值（通过）。 取 Llama-3.1-8B、fp16、$S_{max}=32$（尺寸集 {8,16,32}）。rank-$r$ LoRA 覆盖 q/k/v/o 四个投影、32 层、$d=4096$：每模块 $2 \cdot r \cdot 4096$ 参数，总计 $128 \cdot 2 \cdot 32 \cdot 4096 \approx 3.36\times10^7$ 参数 ≈ 67 MB (fp16)。则 $A_{max}=144$ 占 $144 \times 67\text{MB} \approx 9.7$ GB；$A_{max}=384$ 占 25.7 GB。KV 侧：Llama-3.1-8B 用 GQA（8 KV heads × 128 dim × 32 层 × 2 × 2B）= 128 KB/token。从 144 加到 384，牺牲 16 GB KV ≈ 12.5 万 token 的批处理容量。按 ShareGPT 平均序列长度数百 token 计，这是数百个并发请求的容量。而 §5.1.1 的 throughput plateau 说明超过某点后 batch 增大对吞吐几乎无回报——反过来，减小 batch 一定在 plateau 的陡峭段造成损失。两侧一凑，"$A_{max}$ 超过 ~144 净亏"这个学出来的阈值有独立的物理解释，不是过拟合噪声。

    检查 5 — 排队论：90% 阈值即 $\rho = 0.9$，可反推出 ITL 惩罚（通过，且解释了论文的主要代价）。 $Max_{pack}$ 的定义"吞吐 ≥ 入向 token 速率的 90%"等价于把系统钉在利用率 $\rho \approx 0.9$。对 M/D/1（LLM decode 步长近似确定性），等待时间 $W = \frac{\rho}{2(1-\rho)} \cdot \tau = \frac{0.9}{0.2}\tau = 4.5\tau$；对 M/M/1 则是 $\frac{\rho}{1-\rho}\tau = 9\tau$。也就是说，按定义就要求排队时间是服务时间的 4.5–9 倍。baseline 摊在 4 张卡上时 $\rho \approx 0.45$，M/D/1 下 $W = 0.41\tau$——约一个数量级的排队延迟差。Fig. 11 里 Proposed 的 ITL 系统性劣于 baseline 因此不是实现瑕疵，而是目标函数的直接推论：60% 的 GPU 节省是用 $1/(1-\rho)$ 的延迟放大买来的。论文把这归因于"batch size 更大"，这只是同一现象的另一半表述。

    检查 6 — adapter 加载的带宽预算（不通过：实测远高于 DMA 理论值，说明开销不在链路上）。 rank-8 adapter ≈ 16.8 MB (fp16)，PCIe Gen5 x16 有效带宽约 50 GB/s → 理论 DMA ~0.34 ms；rank-32 约 1.3 ms。论文报告"小请求下 CPU 加载增加 7–16% 延迟"。取小请求为 output≈8 token、TPOT≈25 ms，则请求延迟 $\approx 25 \times 7 = 175$ ms，7% = 12 ms——比 DMA 理论值高 30×以上。结论：加载开销主要不是 PCIe 搬运，而是 vLLM LoRA 加载路径的框架成本（逐 tensor host 拷贝、槽位管理、同步点）。这解释了为什么 $Lat_{load}$ 只能查表拟合而无法解析建模，也意味着该常数是强框架版本依赖的，换 vLLM 版本或换成 zero-copy pinned-memory 路径后 DT 需重新参数化。论文把 disk 加载"当作一次性初始化成本"剔除同样只在 adapter 集合静态时成立；周期性重放置一旦改变 adapter→GPU 归属，冷 adapter 就要重新从 disk 进来（disk 比 CPU 慢 70%）。

    检查 7 — refinement 加速比声明与 Table 5 单元格不完全自洽（不通过）。 声明是"shallow tree 超过 69×，Numba 版最高 2120×"。逐格算：Llama 吞吐 $0.25/3.24\text{e-}3 = 77\times$、$0.25/1.13\text{e-}4 = 2212\times$；Qwen 吞吐 $83\times$ / $2244\times$；Llama starvation $0.16/3.25\text{e-}3 = \mathbf{49\times}$ / $1928\times$；Qwen starvation $68.5\times$ / $0.22/1.05\text{e-}3 = \mathbf{210\times}$。下界 69× 被 Llama starvation 的 49× 违反，上界 2120× 被两个吞吐格的 2212×/2244× 超出。另外 Qwen starvation 的 Numba 版写作 10.5e-4（非常规写法，即 1.05e-3），是唯一没有掉到 1e-4 ms 以下的格子——210× 与其他三格的 ~2000× 差一个数量级，提示这一格可能是笔误或该树未真正走 Numba 路径。精度退化的两个平均值可复现：SMAPE $(5.86+7.61)/2 = 6.735 \approx 6.74$；F1 $(0.03+0.02)/2 = 0.025$，均通过。

    检查 8 — "Original 变体一致更优"被 Table 1 自身证伪（不通过）。 12 个 (模型 × 到达模式 × 指标) 格子里有 6 个 Mean 更优：可预测 TTFT 两行（18.83→17.44、18.95→17.92）、不可预测 TTFT 两行（19.95→19.91、20.74→20.72）、以及不可预测下 Qwen 的吞吐（5.16→5.12）与 ITL（9.87→9.22）。即给 DT 精确的逐请求长度反而让 TTFT 系统性变差。这不是随机波动：TTFT 由请求何时被准入决定，而准入取决于 KV 预算下的排队顺序；喂进真实的长度异质性会让 DT 的贪心 KV 分配在个别长请求上偏离真机的抢占行为，误差被 TTFT 放大而被吞吐（累积量）平均掉。对结论的实际影响是正向的——生产可用的 Mean 模式并不比理想模式差——但论文的表述与自己的表相矛盾。

    检查 9 — 放置耗时与 ML 调用次数不自洽（不通过，量级偏差 ~50×）。 Table 6：Proposed 1.59 s，用 RF（吞吐 0.25 ms、starvation 0.16 ms）。若每次 TestAllocation 是 2 次吞吐 + 1 次 starvation ≈ 0.66 ms，1.59 s 对应约 2400 次 TestAllocation。但结构上界是：11 个测试点 × 4 GPU = 44 次（无回滚时），即使算上回滚重试也难以达到 2400。反过来 ProposedFast 4 ms 配 1.13e-4 ms 的树，若调用次数相同（2400）应只需 0.8 ms，说明其 4 ms 中大部分是排序与簿记等非 ML 成本。两个变体无法用同一套调用次数同时解释，提示 Proposed 的 1.59 s 里含有可观的 scikit-learn 单次调用开销（batch=1 时 predict 的 Python/校验成本远高于 Table 4 报的摊薄值）。这不影响结论方向（4 ms 仍足够周期性重配置），但说明 Table 4 的"预测时延"与 Table 6 的端到端时间不能直接相乘对账。

    检查 10 — 集合通信规模公式（不适用，明确记录）。 常规集群论文要给 $T_{collective}(N)$；本文架构下不存在跨 GPU 集合通信，$N$ 张卡之间零通信，扩展成本项是放置算法本身的 $O(N_{adapter} \log N_{adapter})$ 排序 + $O(|\text{testing points}| \times N_{GPU})$ 次 oracle 查询。真正的扩展性瓶颈不在通信而在两处：(a) DT 数据集生成随 adapter 上限增长（Qwen 因为模型更小能塞更多 adapter，数据集生成反而从 6 小时涨到 9 小时）；(b) ML 模型的特征向量只有 7 维聚合统计量，与 GPU 数无关，因此模型本身可跨规模复用，但贪心的 first-fit 决策质量随 $N_{GPU}$ 增长未被评估（只测到 4 卡）。

    核心技术壁垒（展开） #

    真正难复制的不是任何单个组件，而是「便宜且准的可行性 oracle」这条依赖链的闭环。要联合搜索 $(placement, A_{max})$，必须能在毫秒级判断一个候选配置会不会饿死；这个判据无法解析推导（$Lat_{load}$ 和 $Mem_{max}$ 都只能查表，见检查 6 的分析），只能学；要学就要标注数据；真机每个数据点一小时，而训练网格是 (尺寸三元组 × 到达率十元组 × adapter 数 × $A_{max}$) 的笛卡尔积——真机路线在时间上不成立。DT 把单点成本压到 39 秒才让整条链条闭合（Llama 6 小时、Qwen 9 小时的数据集生成，80 核并行）。换言之，DT 不是一个可有可无的加速器，它是唯一使这个优化问题在数据上可解的环节。第三方要复现，必须先复现 DT 的四个估计器在自己框架版本 / 硬件上的参数化，而 §5.2 的常数拟合依赖的正是那些未公开的 vLLM 插桩指标。

    关键实现细节（易被忽略的两处） #

    1. PrioritySorting 的 zigzag 排序是全文唯一没有任何消融支撑的载荷设计。 排序策略是：先按 adapter 尺寸降序（这一步有明确理由——$S_{max}$ 取同卡最大值，先放大的可以防止后来者抬高整卡的槽位尺寸，从而回溯性地吃掉已放 adapter 的显存），组内再按到达率高低交替排列。zigzag 的作用是让每张卡拿到的到达率分布均衡，避免高速率 adapter 集中在前几张卡上过早触发 starvation 判定、把负载全推给后面的卡。论文对此只写了一句 "selected empirically, as it consistently improved throughput in our experiments"，正文与附录均无对比数据。复现者若换成朴素的到达率降序，很可能得不到 60% 这个数字。

    2. 测试点数组 [8, 16, 32, 64, 96, 128, 160, 192, 256, 320, 384] 被复用为两个语义完全不同的东西。 它既是"每卡累计 adapter 数达到多少时触发一次 TestAllocation"的检查点，也是 NextGPUConfig 返回的 $A_{max}$ 候选集合。这个复用是隐式的（论文只在 §7 用一句 "which reuses the same array of adapter counts defined earlier" 带过），但后果具体：$A_{max}$ 的可行取值被离散化到这 11 个值上，而检查 4 推出的物理最优阈值 ~144 恰好落在 128 与 160 之间——算法结构性地无法选中它。同时因为搜索是"当前值 vs 下一候选"的局部两点比较而非全集扫描，$A_{max}$ 只能单调地沿数组前进，一旦早期选定就无法回退到更小的值（除非整批回滚）。这两点共同解释了为什么会出现 Qwen center-right 那种过保守的误判。
