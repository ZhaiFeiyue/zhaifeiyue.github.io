DECICE: AI-Driven Scheduling and Digital Twin Integration for the Cloud-HPC-Edge Compute Continuum — L2 #

§1 TL;DR #

DECICE 是 Horizon Europe 三年期项目的收官综述：在 Kubernetes 之上做 cloud-HPC-edge 统一调度，两大件是 RNN 预测型 Integrated AI Scheduler（5000×5000 job×node 内 300 s）与融合碳强度/异常预测的 Digital Twin，并用 KSI 桥接 Slurm。

§2 Q1 / Q2 / Q3 #

Q1 痛点：连续体上"资源约束"与"目标函数"不在同一个编排器里 #

论文给出的问题陈述极为紧凑：现代 workload 横跨 IoT 设备、边缘节点、云平台到 HPC 集群，而"workload 必须被匹配到满足计算、内存、数据局部性约束的资源上，同时满足能耗、延迟、成本要求"。这句话里藏着本文真正的工程痛点，值得拆开：

  • 约束侧（硬）：computational / memory / data locality — 这三项都是 Kubernetes 原生 scheduler 能表达一部分的（requests/limits、node affinity），但 data locality 在跨 HPC-cloud-edge 场景下不再是"同一个 CNI 网段内的拓扑"，而是跨机构、跨传输介质的问题。
  • 目标侧（软）：energy / latency / cost — 这三项 Kubernetes 默认调度器完全不表达。绿电可用性、节点级功耗、碳强度都不是 K8s 的一等公民。

痛点因此不是"调度算法不够好"，而是编排面缺少描述这些量的状态源。这解释了为什么本项目的两个核心组件里有一个不是调度器而是 Digital Twin：先要有可查询的实时能耗/碳强度/异常状态，能耗感知调度才有输入。

另一个隐含痛点在 HPC 侧：HPC 集群由 Slurm 管理、通常不给用户 root、不允许运行标准容器运行时，因此 cloud-native 的 workload 无法直接落到 HPC 分区。论文把这一段能力单独归给 WP3 的 KSI（Kubernetes-Slurm Integration，"enabling Kubernetes workloads on rootless HPC systems"）。

Q2 方法：一个 K8s 控制面 + 可插拔调度策略池 + 状态孪生 #

论文的方法是分层而非单点，可以按 Fig. 1 的两个平面读：

  1. DECICE Framework 平面（控制面）：两个入口 API（DECICE API (Job & Telemetry) 面向 End User，DECICE API (Control & Security) 面向 Admin）→ DECICE Control Manager → DECICE Model。DECICE Model 内部并列放着 Digital Twin 与三个调度器：AI Scheduler、Heuristic Scheduler、Gang Scheduler。旁挂 DECICE Config Store 与 Metrics Storage (Prometheus)，以及两块 Platform Specific Glue Code（Wrapper / Scheduler）。
  2. Compute Plane (K8s) 平面（数据面）：HPC（HPC Nodes + Frontend Nodes 带 Proxy）、Cloud、Master Nodes（KubeAPI、KubeEdge CloudCore）、Edge（EdgeCore）四个域，每个节点组都挂 Kubelet + Monitoring。

    3. IAIS（Integrated AI Scheduler）内部包含三条技术路线，论文明确它们是并列策略而非替代关系：

    • HOSHMAND：RNN-based，从历史 job-resource state pair 学习最优分配，目标是"eliminate redundant scheduling computations" —— 即把重复出现的调度决策变成一次前向推理而不是一次重新求解。
    • GrapheonRL：GNN + RL，把 workflow 建成 dependency-aware graph，声称能做 constraint-aware scheduling "without mathematical reformulation"（即不需要每换一组约束就重写 MILP 模型）。
    • workflow-driven modeling framework：把异构 HPC 调度形式化分解为 task-node mapping 与 schedule derivation 两步，并在这个框架下横向 benchmark 精确解算器（PuLP / SCIP / Gurobi / OR-Tools）、约束规划（CP-SAT）与启发式（GA / PSO / ACO / SA / HEFT / OLB）。

    Digital Twin（Fig. 3）是一个以 InfluxDB 为中心的状态孪生：Digital Twin Core (DTC) 维护 Digital Twin Cluster Status，通过 TimeSeriesClient 读写时序库；上挂三个 ML 模型（Carbon Intensity Prediction、Node Anomaly Detection、Workload Energy Prediction），下挂 DT Clients（Scheduler Controller、Control Manager、PromQL-to-Json Wrapper Service、VTE）。API Server 只暴露 POST Cluster Snapshot / GET Cluster Snapshot 两个动作。

    核心技术壁垒：不是 RNN，也不是 GNN+RL——这两者都在引用文献里，本文只做集成。真正难复制的是把"预测型状态源"做成调度器可同步查询的一等接口，并让它同时服务于真实集群与虚拟测试环境（VTE）。Fig. 3 里 Scheduler Controller 与 VTE 挂在同一个 DT Clients 平面上、共用同一套 snapshot 语义，这意味着 AI 调度器的训练环境与生产环境看到的是同一形状的状态对象。这一点是 sim-to-real 的关键：Fig. 2 里 LB-KAIROS（图内绘制为 LiI-KAIROS）能"simulating several load-balancer and scheduling methods for validation"，其可信度完全建立在 VTE 与真实集群共享 DT snapshot schema 之上。任何想复现 DECICE 的团队都得先重建这个双端一致的状态抽象，而这一层论文没有给形式化定义，只给了框图。

    Q3 结果 #

    • IAIS 可扩展性：从 10 jobs×10 nodes 到 5000×5000，最大规模 100% 利用率下模型执行时间仍在 300 s 内（图中最大打印值为 5000×5000 (50%) 的 training 297.974 s）。
    • 求解器 benchmark：Workflow 3（高依赖数）下 PuLP 25.46 s、OR-Tools 27.65 s，而 Gurobi 因内部 presolving 仅 1.41 s；HEFT 0.01–0.02 s。
    • 项目级产出：>15 篇同行评审论文、全部组件开源（https://github.com/DECICE-project）、ISC-HPC 2024/2025 tutorial 覆盖 >100 人。
    • 用例验证：cloud robotics（Marmara/BIGTRI）、scientific computing（KTH/PDC）、edge inference（未指定 owner）——但这三个用例在本文内没有任何量化数据，只在 §II/§IV 被点名。

    3.1 整体架构（原图） #

    Paper's Figure 1, verbatim (caption: "DECICE framework architecture integrating contributions from all work packages.     3.2 请求生命周期（重绘：原文无此视角图） #

    原文三张框图都是静态结构图，没有一张给出 job 从提交到落盘的时序。下面按 Fig. 1 + Fig. 2 + Fig. 3 的箱体与边标签还原一次生命周期：

    sequenceDiagram participant U as End User participant API as DECICE API (Job & Telemetry) participant CM as Control Manager participant DT as Digital Twin Core participant S as AI Scheduler (IAIS) participant K as KubeAPI / Kubelet U->>API: submit workflow (K8s / Snakemake / Argo) API->>CM: normalized job + constraints CM->>DT: GET Cluster Snapshot DT-->>CM: state + carbon / energy / anomaly forecast CM->>S: job attrs + node attrs + snapshot S->>S: ETL -> features & sequences -> RNN inference S->>S: (optional) LB-KAIROS simulation for validation S-->>CM: best predicted scheduling strategy -> placement CM->>K: bind pods (HPC via Proxy / Cloud / EdgeCore) K-->>DT: POST Cluster Snapshot (Prometheus metrics)

    关键在于 GET Cluster Snapshot 出现在调度决策之前、POST Cluster Snapshot 出现在绑定之后：这条闭环是 energy-aware 调度得以成立的结构前提，也是 Digital Twin 不能被降级为监控看板的原因。

    3.3 IAIS 数据流（原图） #

    Paper's Figure 2, verbatim (caption: "WP2: IAIS data flow. Heterogeneous node and job attributes enter through ETL, pass through the AI scheduler's RNN model and LB-KAIROS simulation, producing Kubernetes-compatible placement decisions.")

    两路输入（节点属性：CPU/GPU 数据、容量、当前状态；作业属性：CPU/GPU 需求、内存、运行时）经 ETL 变成 Features and Sequences，说明 RNN 的输入是序列化的调度历史而非单帧快照——这与 HOSHMAND"从历史 job-resource state pair 学习"的定位一致。虚线框内 Succeed Strategies and Prior Data 是一个数据库柱体，意味着"成功策略"被持久化并回灌训练，这是"消除冗余调度计算"的实现方式：命中历史相似状态则直接复用策略。输出经 DP（data preparation）适配到 Kubernetes 或其他 API，即调度器本身不与 K8s 强绑定。

    六项最小核对（在无形式化模型前提下逐条判定）：

    1. 量纲一致性 — 不适用（无方程）。Fig. 4 / Fig. 5 的 y 轴均为秒，量纲自洽。
    2. 极限行为 — 可部分检验：$J=N=10$ 时训练 0.703–1.38 s，$J=N=5000$ 时 275.851–297.974 s。规模放大 500× 而时间放大约 200–400×，即经验上呈次二次增长；但只有 4 个规模点（10/100/1000/5000），拟合任何指数都不充分。
    3. 单调性 — 被数据违反：5000×5000 下 50% 利用率（297.974 s）慢于 100%（275.851 s）与 >100%（285.527 s）。若存在模型，此处需要解释；论文未提。
    4. 边界条件 — Fig. 4 的 x 轴包含第三档 >100 % 利用率，caption 与 §III 正文均未定义"超过 100% 的资源利用率"含义（超订？排队？），属未定义边界。
    5. 与实验数值的一致性 — §III 称"execution completes within 300 seconds"，最大打印值 297.974 s，一致但余量仅 0.7%，该论断对 5000×5000 之外的规模不具外推力。
    6. 文-图一致性 — 存在不一致：正文称"Heuristics (GA, PSO, ACO, SA, HEFT, OLB) maintain sub-second runtimes throughout"，而同一张 Fig. 5 中 PSO 为 3.89 / 4.59 / 4.13 s、SA 为 3.92 / 4.71 / 4.65 s，三个场景全部超过 1 s。该句为 §III 关于启发式的头条论断。

      5.5 Baseline 公平性 #

      本文的 baseline 不是竞品框架，而是求解器软件本身（PuLP / SCIP / Gurobi / OR-Tools / GA / PSO / ACO / SA / HEFT / OLB），且这 10 个工具都没有单独引用。因此无法核对：版本号（Gurobi 的 presolving 行为强依赖版本与 license 等级）、超参（GA/PSO/SA 的种群大小与迭代数直接决定其 runtime，PSO 的 3.89 s 很可能只是迭代数设置的产物）、硬件（未报告 CPU 型号、核数、内存）。指标定义同样宽松：Fig. 4 的"execution time"未区分单次 epoch 与全量训练；Fig. 5 的"run-time"未说明是否包含模型构建（build）时间——而对 MILP 而言 build 时间常与 solve 时间同阶。没有 DECICE 与 vanilla Kubernetes 调度器的端到端对比实验。

      7.1 核心技术壁垒（对应 §2 Q2） #

      最难复制的一环是真实集群与虚拟测试环境共享同一 snapshot 契约。Fig. 3 把 Scheduler Controller 与 VTE 并列挂在 DT Clients 平面，二者都通过 API Server 的 POST / GET Cluster Snapshot 与 DTC 交互；Scenario DB 经 SQL-to-Json 喂 VTE，形状与真实 PromQL-to-Json Wrapper Service 的输出对齐。这个设计的后果是：Fig. 2 中 LB-KAIROS 做的调度方法仿真、以及 RNN 的离线训练，都可以在与生产同构的状态对象上进行，训练-部署之间不存在特征漂移。要复制 DECICE，重写一个 RNN 或换一个 GNN 都不难，难的是先把这套双端一致的状态抽象定义出来并保持长期兼容——而这一层论文只给了框图，既无 schema 定义、无字段列表、无版本化策略，也没有说明 snapshot 的采样周期与一致性语义（快照是否跨节点原子）。这是复现该框架时最大的未公开面。

      7.2 关键实现细节（易被忽略的两处） #

      1. JSON 是 DT 的对外契约，PromQL 不是。 Fig. 3 中 Monitoring System 不直连 DTC，而必须经 PromQL-to-Json Wrapper Service 转换后才进入 DT client 平面。这意味着监控后端是可替换组件（换掉 Prometheus 只需重写 wrapper），但也意味着所有查询表达能力被压缩到 wrapper 暴露的那一组固定 JSON 字段——PromQL 的即席聚合能力在 DT 侧不可用。任何需要新聚合维度的调度策略都要改 wrapper 而非改查询。
      2. HPC 域的 Frontend Nodes → Proxy 是唯一可控入口。 Fig. 1 中 HPC 子域比 Cloud 子域多出一层：Cloud Nodes 直接跑 Kubelet + Monitoring，而 HPC 侧在 HPC Nodes 之外另有 Frontend Nodes 承载 Proxy。这是 rootless HPC 的必然产物——计算节点上无法运行需要特权的组件，只能由登录/前端节点代理。实践含义是 HPC 分区的调度延迟与吞吐上限由这个 proxy 决定，它是单点也是瓶颈，而论文既未测量它也未讨论其 HA。

        3. 另有两处命名与一致性问题会在对照代码时造成困扰：Fig. 2 的 caption 写 LB-KAIROS，图内绘制为 LiI-KAIROS，全文未展开该缩写；WP2 的 lead"after transfer from FBU"，而 FBU 不在 §I-A 的 12 家伙伴名单中。查找对应仓库时这两个名字都不可靠。
