MetaGPT: Meta Programming for a Multi-Agent Collaborative Framework — L2 #

1. TL;DR #

将人类软件公司的 SOP 编码进 prompt 序列,把复杂任务拆给 5 个专职 agent(PM/架构师/项目经理/工程师/QA),用共享消息池 + 发布-订阅传递结构化文档(而非自由对话),再加可执行反馈自纠错。HumanEval/MBPP Pass@1 达 85.9%/87.7%(SoTA),SoftwareDev 可执行性 3.75、人工修订成本降到 0.83。

2. Q1 / Q2 / Q3 #

Q1 — 痛点 #

朴素地把多个 LLM 串成对话式多智能体,会因级联幻觉(cascading hallucination)导致逻辑不一致:每一轮自由对话都像"传声筒游戏"逐渐扭曲原始信息,还会陷入"重复指令"或"消息无限循环"。此前的角色扮演框架(CAMEL、ChatDev)只能解决简单对话任务,无法系统性地把抽象需求拆解为可执行的复杂软件工程。

Q2 — 方法 #

把领域内经过人类长期协作沉淀的 Standardized Operating Procedures(SOP) 编码为 prompt 序列,让每个 agent 承担明确角色并产出结构化中间制品(PRD、数据结构、接口定义、序列流程图),而非自由聊天。角色间通过全局共享消息池 + 基于角色 profile 的发布-订阅传递这些文档;工程师用可执行反馈(executable feedback)循环:写码→跑单元测试→报错则对照 PRD/设计/历史记忆调试,最多重试 3 次。

核心技术壁垒:让 SOP 落地为一组可被 LLM 稳定消费的结构化 schema 交接契约——每个角色的输出被约束成下游角色能直接解析的规范文档(File List、Data Structure、Interface Definition、Sequence Flow),从而把"传声筒式"信息损耗压到最低。这不是简单加角色,而是设计一套让抽象需求逐级具体化、且每级都可校验的中间表示。详见 §7。

Q3 — 结果 #

HumanEval/MBPP 单次尝试 Pass@1 达 85.9%/87.7%,超过所有基线(含 GPT-4 原生);在自建 SoftwareDev 上可执行性 3.75(满分 4)、人工修订成本 0.83(ChatDev 为 2.5),100% 任务完成率。可执行反馈单独带来 +4.2%/+5.4% Pass@1 提升。

MetaGPT 的每一轮 SOP 交接遵循固定的"观察消息池 → 依赖满足则触发 → React 式行动 → 产出结构化文档 → 发布回池"状态机:

规划与推理:规划风格为预定顺序工作流(predetermined workflow)而非树搜索——SOP 把任务拓扑固定为 PM→架构师→项目经理→工程师→QA 的线性流水线;分解是自顶向下(需求→子任务→类/函数);预算体现在工程师的调试子循环上限(max 3 retries);回溯仅存在于工程师节点内(基于历史执行/调试记忆),跨角色不回溯。所有 agent 遵循 ReAct 式(think-then-act)行为。

4. 作者证明 #

无形式化作者证明 — 仅实证。 论文唯一的形式化对象是评测指标(无偏 Pass@k 估计量),而非方法本身的收敛/成功率保证。可被 bound 却未 bound 的量:多角色流水线的端到端成功率、级联幻觉的传播概率上界——论文只以实证 sweep 呈现单调性。

符号表(唯一公式 Pass@k):

符号含义
$n$每个问题生成的样本总数
$c$$n$ 个样本中正确的个数
$k$考虑的 top-k 样本数
$\binom{\cdot}{\cdot}$二项式系数
$\mathbb{E}_{\text{Problems}}$在基准问题集上取期望

方程物理意义:

$$\operatorname{Pass}@k = \mathbb{E}_{\text{Problems}}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]$$

其中 $\frac{\binom{n-c}{k}}{\binom{n}{k}}$ 是从 $n$ 个样本随机抽 $k$ 个全错的概率,故 $1-(\cdot)$ 是至少有一个正确的概率;在问题集上取期望即无偏 Pass@k,避免直接在 $k$ 个样本上估计的高方差。

6 项最小检查:

  1. 量纲:$\binom{n-c}{k}/\binom{n}{k}$ 为无量纲概率,$\operatorname{Pass}@k \in [0,1]$。✓
  2. 边界 $c=0$(无正确样本):分子 $\binom{n}{k}$=分母,比值为 1,Pass@k=0。✓ 物理合理。
  3. 边界 $c\ge k$ 且极端 $c=n$:分子 $\binom{0}{k}=0$,Pass@k=1。✓
  4. 单调性:$c$ 增大 → 全错概率减小 → Pass@k 增大。✓ 与"正确样本越多越易命中"一致。
  5. 一致性($k=1$):退化为 $\mathbb{E}[c/n]$,即平均正确率。✓
  6. 与实证一致:执行反馈把 Pass@1 提升 4.2%/5.4%(Figure 4),符合"更多可执行正确样本 → 更高 Pass@1"。✓

Success-rate sweep(实证):论文沿 (角色数, backbone 模型, 指令详略) 三轴 sweep。角色轴(Table 3):Engineer 单角色 → 4 角色,可执行性 1.0→4.0、人工修订 10→2.5,基本单调改善(但 3 角色配置里"加架构师"executability 2.5 > "加项目经理"2.0,非严格单调)。backbone 轴(Table 5):GPT-4 executability 3.8 > GPT-3.5 2.8 > Deepseek Coder 33B 1.4,强单调依赖后端能力。指令轴(Table 6):详细 prompt 4.0 略优于高层 prompt 3.8。

    7. 实现 cross-reference #

    核心技术壁垒(§2 Q2 呼应):最难复制的不是"多角色"这一表层设计,而是把每个角色输出约束成下游可稳定解析的结构化 schema(PRD 的 User Stories/Requirement Pool、架构师的 File List/Data Structure/Interface Definition/Sequence Flow)。正是这套逐级具体化、每级可校验的中间表示,把自由对话的"传声筒"损耗替换为文档化交接,才使复杂需求能可靠地落到类/函数级实现。缺了这层 schema 契约,单纯加角色只会放大级联幻觉。

    关键实现细节(易被忽略的 tricks):

    1. 发布-订阅是定向的:agent 只在收齐其全部前置依赖后才激活行动(§3.2),且按角色 profile 过滤消息(架构师订阅 PRD、忽略 QA 输出),这是避免信息过载的关键,而非把消息池当广播。
    2. 可执行反馈的重试上限为 3(§3.3):工程师复用自身历史执行/调试记忆迭代,而非无限循环;这个硬上限是把"自纠错"与"无限消息循环"失败模式区隔开的隐性设计。

      3. 实现引用:开源实现见 https://github.com/geekan/MetaGPT (L1 §0 Abstract、§1 para 6 均给出项目地址)。L1 未记录具体 file:line;方法级实现对应 §3.1(角色/profile 初始化)、§3.2(消息池+订阅接口)、§3.3(executable feedback action)。[实现未公开] 到 file:line 粒度。
